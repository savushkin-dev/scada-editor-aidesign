## 1. Что делает проект

Система **генеративного дизайна HMI-мнемосхем** для АСУ ТП молочного/сыродельного производства.

**На входе:**
- **PDF** — технологическая схема (P&ID), выгруженная из Eplan. Содержит векторную графику
  (линии/прямоугольники/кривые) и текстовые метки устройств (`V1`, `LS2`, `FQT1`, `=A1+CIP` …).
- **Lua-файлы описания контроллера**, выгруженные из EPlanner:
  - `main.io.lua` / `main.wago.lua` — IO-узлы (`nodes`) и физические устройства (`devices`);
  - `main.objects.lua` — технологические объекты, режимы работы (операции), состояния и шаги.

**На выходе:**
- **JSON для редактора мнемосхем** — плоский массив элементов холста: линии чертежа
  и устройства с их именами. Это то, что читает конечный проект;
- **XML или `*.plant.json`** (`PlantGeometry`, версия 1.3) — размеченная схема целиком:
  техобъекты, их контуры, устройства с координатами и характеристиками, трубопроводы,
  точки сопряжения, встроенный SVG;
- либо **PostgreSQL** — те же данные в 4 таблицах;
- промежуточные **JSON** (`output/parsed_lua.json`, `output/parsed_lua_objects.json`).

Смысл: связать *геометрию схемы* (что где нарисовано) с *логикой контроллера*
(какое устройство к какому техобъекту относится, что оно делает в каждой операции) и получить
машинно-читаемое описание, из которого можно генерировать мнемосхемы/HMI.

## 2. Структура каталогов

Код лежит одной папкой — ниже её состав. Исходные материалы (чертежи Eplan,
выгрузки контроллеров, библиотеки фигур, эталоны экспорта) держат рядом,
в папке `doc`: они весят гигабайты и в репозиторий не входят.

Код собран в пакет `contur`, подпапки которого идут по ходу конвейера: `pdf`
разбирает чертёж, `lua` — описание контроллера, `matching` связывает одно
с другим, `scene` сводит это в разобранный лист, `export` и `hmi` отдают
результат, `ui` показывает его в окне. `core` — общий фундамент, он
ни от кого не зависит.

`export` и `hmi` — соседи, а не вложенные друг в друга. В `export` три
записи одного и того же PlantGeometry 1.3 (XML, JSON, PostgreSQL) плюс
чтение своего XML обратно; в `hmi` — другая модель с отдельной
спецификацией, своим каталогом фигур и своей приёмкой. Выбор формата
по расширению файла стоит над обоими, в `contur/exporters.py`.

Сцена стоит отдельным слоем, а не внутри выгрузки, потому что она —
результат всего конвейера, и читают её одинаково и четыре выгрузки,
и главное окно:

```
pdf ─┐                        ┌─→ export ─┐
     ├─→ matching ─→ scene ─→ ┼─→ hmi ────┴─→ exporters
lua ─┘                        └─→ ui
```

Зависимости направлены только вниз по этому списку, вверх — ни одной.

## 3. Форматы входных данных

### 3.1 `main.io.lua` / `main.wago.lua` — «железо»
```lua
PAC_name = 'BN1-Молокохранилище'
nodes = { { name='A1', ntype=201, n=1, IP='10.170.98.140', modules={ {2688048}, … } }, … }
devices = {
    { name='CIPV16', descr='Дренаж', dtype=0, subtype=13,
      article='OMR.E2A-S12KS04-M1-B1',
      DI={{node=3, offset=4614, physical_port=6, logical_port=7, module_offset=4608}},
      AO={{…}}, rt_par={6,2}, par={5000, 1} },
    …
}
```
Парсится **исполнением** через `lupa.LuaRuntime` (`parse_lua.py:60`), затем Lua-таблицы
рекурсивно конвертируются в python (`lua_table_to_python`). Читается с автоопределением кодировки
(utf-8 → cp1251 → latin-1 → cp866 → windows-1251).

Ключ имени устройства: `name = <ТЕХОБЪЕКТ><ТИП><НОМЕР>`, например `LA_TANK1` + `V` + `101`.

### 3.2 `main.objects.lua` — «логика»
```lua
init_tech_objects_modes = function()
    return {
    [1] = { n=1, tech_type=1, name='Мастер', name_eplan='MASTER', name_BC='MasterObj',
            base_tech_object='master',
            par_float = { [1] = { name='Время операции', value=0, meter='мс', oper={-1}, nameLua='OPERATION_TIME' }, … },
            equipment = {…}, properties = {…}, system_parameters = {…},
            modes = { [1] = { name='Мойка', base_operation='…', props={…},
                              states = { [1] = { name='…', opened_devices={…}, closed_devices={…},
                                                 devices_data={…}, DI_DO={…},
                                                 steps = { [1] = { name='Шаг 1', opened_devices={…},
                                                                   closed_devices={…}, time_param_n=…,
                                                                   next_step_n=…, jump_if=…, … } } } } } } }
    }
end
```
Парсится через **lupa** (`parse_objects_file`): файл выполняется, вызывается
`init_tech_objects_modes()`, результат переводится в Python с учётом того, какие поля
являются отображениями (`modes`, `states`, `steps`, `par_float`, `properties`,
`system_parameters`, `equipment`), а какие — массивами.

`extract_all_data()` разворачивает вложенность в плоские списки:
`tech_objects`, `devices`, `operations`, `states`, `steps`, `signals`, `parameters`.

**Иерархия ID:** `operation.id = "{obj_id}_{mode_id}"`, `state.id = "{operation_id}_{state_id}"`,
`step.id = "{state_id}_{step_id}"`, например `2_4`.

### 3.3 PDF
Схема Eplan. Важные соглашения, на которые опирается код:
- **контуры техобъектов рисуются пунктиром** (`dashes` в `page.get_drawings()`);
- имя контура — текст с `+`, формат Eplan `=XX+ИМЯ` → берётся часть после `+`;
- метки устройств — короткие тексты (≤10 символов) вида буква+цифра (`V7`, `LS2`, `FQT1`).

## 4. Архитектура и конвейер обработки

```
 ┌── Lua (main.io.lua) ──► parse_lua.py (lupa) ─────────► output/parsed_lua.json
 │                                                             │  {nodes, devices}
 │                                                             ▼
 ├── Lua (main.objects.lua) ► parse_lua_objects.py ──► output/parsed_lua_objects.json
 │                                (LuaTableParser)             │  {tech_objects, operations,
 │                                                             │   states, steps, …}
 │                                                             ▼
 │                                                    objects_loader.objects_data
 │                                                    (операции/состояния/шаги в GUI)
 │
 └── PDF ─┬─► extract_geometry.py ──► сегменты + тексты
          │        │
          │        ▼
          │   contour_detector.find_contours()  (только пунктирные линии → граф → циклы)
          │        │
          │        ▼
          │   find_all_contour_names_by_proximity()  (имя контура; приоритет — совпадение с Lua)
          │        │
          │        ▼
          │   gen_xml() ──► временный GeometryData.xml (Segments + ClosedContours)
          │        │
          │        ▼
          │   device_matcher.match_devices()  ──► List[DeviceMatch]
          │        (текст внутри bounds контура + имя есть в Lua-устройствах техобъекта)
          │
          └─► pdf_processor.DeviceDetector (общий для CLI и GUI):
                   PDF → PNG (200–300 dpi) → YOLO по плиткам 1024/шаг 768,
                   с покрытием краёв, пропуском пустых плиток и объединением
                   дублей по IoU → bbox устройств → перерисовка PDF в SVG:
                      линии внутри bbox = red (устройства), остальные = blue (трубопроводы)

                        DeviceMatch[] + Contour[] + размеченный SVG
                                        │
                                        ▼
                              svg_geometry.py (общий модуль)
                     сегменты · точки сопряжения · трубопроводы
                                        │
                        ┌───────────────┴────────────────┐
                        ▼                                ▼
                xml_export.py                    postgreSQL_export.py
          PlantGeometry XML v1.3            contours / devices / connections
        (+ JunctionPoints, Pipelines,           / junction_points
           SVGContent в CDATA)
```

Вся работа с геометрией размеченного SVG (определение масштаба, извлечение сегментов,
поиск точек сопряжения, сборка труб) живёт в **`svg_geometry.py`** и используется всеми
тремя потребителями. Поиск соседних объектов идёт через пространственную сетку
(`SpatialGrid`), а не перебором пар.

### Точка входа — `main.py` и `contur/ui/main_window.py`

GUI на PySide6, окно `DeviceVisualizer` (`contur/ui/main_window.py`). Вся тяжёлая работа — в `QThread`:

| Поток | Файл:строка | Что делает |
|---|---|---|
| `LuaParsingThread` | `workers.py` | main.io.lua → `output/parsed_lua.json` |
| `LuaObjectsParsingThread` | `workers.py` | main.objects.lua → `output/parsed_lua_objects.json` |
| `GeometryExtractionThread` | `workers.py` | PDF → сегменты/тексты → контуры → имена → временный XML |
| `DeviceMatchingThread` | `workers.py` | Lua + контуры + тексты → `DeviceMatch[]` |
| `YOLOMarkingThread` | `workers.py` | PDF → PNG → YOLO → размеченный SVG (red/blue), с кэшем; прерывается `requestInterruption()` |
| `PostgresExportThread` | `workers.py` | выгрузка в базу; раньше шла в потоке окна и подвешивала его |
| `PageTitlesThread` | `workers.py` | названия листов из штампа для списка страниц (265 листов ≈ 4 с) |

Загрузка PDF автоматически запускает `GeometryExtractionThread` → по завершении
`_start_device_matching()`. После сопоставления `_markup_if_cached()` проверяет ключ
кэша и молча показывает готовую разметку; новый лист ждёт `Ctrl+M`.

**UI:** меню «Файл / Обработка / Экспорт / Вид»;
левая панель — загрузка, список схем, переход по листам, профиль разметки, фильтр,
переключатели слоёв, легенда типов, мини-карта, поиск и дерево устройств;
центр — `GraphicsView` (SVG-подложка + контуры + кружки устройств);
низ — `OperationsBrowserWidget` (дерево «объект → операция → состояние → шаг»).
При выборе операции устройства подсвечиваются по состоянию
(`opened` / `closed` / `not_used`) — `on_operation_selected_for_devices`.

**Горячие клавиши**: `Ctrl+O` Lua, `Ctrl+Shift+O` объекты, `Ctrl+P` PDF,
`Ctrl+M` разметить, `Esc` прервать, `Ctrl+R` отчёт, `Ctrl+E` выгрузка (JSON, XML), `Ctrl+D` база,
`Ctrl+F` поиск, `F` вписать схему. Раньше это были одиночные буквы без модификатора,
из-за чего в окне нельзя было завести ни одного поля ввода.

**Перемещение по схеме**: зажатое колесо или пробел+ЛКМ, стрелки (Shift — крупнее),
колесо и `+`/`−` — масштаб, двойной щелчок или `Home` — вписать.

**Что помнится между запусками** (`app_settings.py`, QSettings): размеры окна,
положение разделителей, последние папки и файлы, профиль разметки, настройки
отображения, параметры базы без пароля, прошлый сеанс. Файлы принимаются
перетаскиванием в окно.

## 5. Ключевые алгоритмы

### 5.1 Поиск контуров — `contour_detector.find_contours()`
Берутся **только пунктирные** сегменты. Точки нормализуются к сетке `TOLERANCE = 0.5`,
строится граф «точка → (соседняя точка, id сегмента)». Обход от вершин степени 2, пока не
вернулись в старт и цикл ≥ 3 сегментов → `ClosedContour` с bounds/center.

### 5.2 Именование контуров — `find_all_contour_names_by_proximity()`
Контуры сортируются по площади (сначала мелкие). Для каждого — кандидаты из текстов с `+`,
дальше скоринг по расстоянию до сегментов контура с множителями:

| Условие | Множитель score (меньше = лучше) |
|---|---|
| найден в Lua **и** текст внутри контура | ×0.1 |
| найден в Lua | ×0.3 |
| текст внутри контура | ×0.8 |
| иначе | ×1.0 |

Совпадение с Lua ищется по `name_eplan` / `name_BC` (upper-case), плюс эвристики
`TANK1 → TANK`, `M1 → M` (`find_best_lua_match`). Один текст используется только один раз.

### 5.3 Сопоставление устройств — `device_matcher.match_devices()`
1. Все Lua-устройства разбираются регуляркой `^(.+?)(V|DI|DO|AI|AO|M|LS|LT|TE|QT|FQT|PT|PC)\d+$`
   → `{tech_object: {короткое_имя: device}}`.
2. Из имени контура берётся `tech_object` (часть после последнего `+`).
3. Тексты PDF внутри контура сравниваются с ожидаемыми короткими именами.
   Совпало → `DeviceMatch(confidence=1.0)` с подтягиванием `descr`, `article`,
   `category`, `subtype`, `dtype` из Lua.

Попадание в контур проверяет `is_text_in_contour`: сначала дешёвый отсев по `bounds`
(допуск `TOLERANCE = 5.0`), затем трассировка луча по сегментам самого контура
(`is_point_inside_polygon`). Учитывается реальная форма — у П-образных и вложенных
контуров подписи из чужой области больше не засчитываются.

Список типов устройств — в `config.DEVICE_TYPES`, дополняется переменной
`CONTUR_DEVICE_TYPES`. Длинные обозначения проверяются первыми, иначе `FQT`
разберётся как `QT`.

**Отчёт о расхождениях** (`build_match_report` / `format_match_report`) показывает,
что не сошлось: устройства из Lua, не найденные на чертеже; подписи на чертеже без
устройства в Lua; имена, не разобранные по типу; техобъекты с других листов.
Доступен кнопкой в GUI (с сохранением в файл) и флагом `--report` у `check_pipeline.py`.

### 5.4 YOLO-разметка — `pdf_processor.DeviceDetector` (используется и GUI, и CLI)
- Выбранная страница PDF → PNG (300 dpi в GUI, 200 dpi в `pdf_processor.py`);
- скользящее окно и DPI задаются **профилем** (`config.YOLO_PROFILES`):
  `fast` (200 dpi, плитка 1024, ~40 с на лист A0) и `accurate` (200 dpi, плитка 512,
  ~2 мин, вдвое меньше сомнительных детекций). Профиль выбирается в окне
  рядом с кнопкой разметки или переменной `CONTUR_YOLO_PROFILE`;
- размер плитки отделён от размера входа сети (`YOLO_IMGSZ`, 1024 — как при обучении);
- модель ищется через `config.find_yolo_model()`, `conf=0.25`;
- **класс** (`valve` / `sensor` / `pump`) и **уверенность** читаются и доходят
  до устройства: объединение дублей — обычный NMS по уверенности, в XML пишется
  реальная `confidence`, класс сверяется с типом из подписи;
- дубли объединяются по IoU ≥ 0.5 **и** по «пересечение к меньшей площади» ≥ 0.8 —
  второе нужно для вложенных рамок (89×89 внутри 200×200 даёт IoU всего 0.198);
- плитки прижимаются к правому и нижнему краю, чтобы лист был покрыт целиком;
- заведомо пустые плитки не отправляются в модель, остальные идут пачками по 4;
- рамки одного устройства из перекрывающихся плиток объединяются по `IoU ≥ 0.5`;
- bbox пересчитываются PNG → PDF-пункты (`scale = pdf_width / png_width`);
- PDF перерисовывается в SVG: примитив внутри bbox → `stroke="red"` (устройство),
  иначе `stroke="blue"` (трубопровод). Прямоугольник разбирается на 4 линии.
- Имя устройства даёт `DeviceLabeler`: пары (рамка, метка) сортируются по близости
  и раздаются жадно, **каждая метка достаётся одному устройству**. Метка внутри
  рамки в приоритете, метка с типом, противоречащим классу модели, считается
  втрое более далёкой. Имя, класс и уверенность пишутся в SVG атрибутами
  **`data-device-name`**, `data-device-class`, `data-device-conf` — без них
  связь «устройство ↔ труба» теряется.

Результат разметки кладётся в **`markup_cache`**: ключ учитывает файл (размер и время
изменения), страницу, модель, параметры нарезки и генератор. Повторная разметка того же
листа — мгновенно вместо ~30 с. Отключается `CONTUR_DISABLE_CACHE=1`, папка —
`CONTUR_CACHE_DIR` (по умолчанию `output/markup_cache`).

### 5.5 Точки сопряжения и трубопроводы (`svg_geometry.py`)
- **JunctionPoint** — конец красной линии и конец синей ближе `JUNCTION_TOLERANCE = 10.0`;
  точка = среднее. Одна пара red/blue учитывается один раз. Кандидаты берутся из
  пространственной сетки с ячейкой в размер допуска (9 ячеек вместо всех синих линий).
- **Pipeline** — связные цепочки синих сегментов (`build_pipelines`, обход в ширину
  по общим концам), с сортировкой сегментов в цепочку, суммарной длиной и списком
  подключённых устройств. Устройства для всех сегментов считаются один раз,
  а не заново для каждой трубы.
- Перед этим отфильтровываются «линии рамки»: всё, что выходит за 3 % … 97 % холста.

`extract_line_segments` разбирает `<line>`, `<rect>` (в четыре линии) и `<path>`
с командами M/L/C — у кубических кривых берётся хорда.

Принадлежность линии устройству — по доле длины внутри рамки
(`segment_box_overlap`, отсечение Лианга-Барски, порог 0.5), а не по попаданию
середины отрезка.

Допуски масштабируются под размер устройства: генератор пишет в SVG
`data-device-size`, `tolerance_scale` пересчитывает их относительно эталонных
32 пт (`REFERENCE_DEVICE_SIZE`).

**Имена устройств в связках.** Подпись на схеме короткая (`V1`) и повторяется у каждого
техобъекта, поэтому сама по себе связь не идентифицирует. `resolve_device_names`
сопоставляет её с ближайшим распознанным устройством и подставляет полное имя из Lua
(`TANK1V11`).

**Положение устройств.** `device_centers` собирает геометрию устройства из красных
сегментов с одинаковой подписью, лежащих рядом; `snap_devices_to_geometry` переносит
точку устройства с центра текстовой метки в центр самого устройства (метка нарисована
рядом с устройством, а не на нём).

### 5.6 Система координат — важный узел
SVG бывает в PDF-пунктах либо отмасштабирован (`pdf_processor` пишет с `scale_factor=1.25`,
GUI — 1:1). Масштаб определяет `detect_coordinate_system(svg_root, pdf_size)`:

- если передан **`pdf_size`** — реальный размер страницы PDF, — масштаб считается точно;
- иначе подбирается по стандартным форматам A0…A4/Letter/Legal. Подбор неоднозначен:
  у всех ISO-форматов одинаковое соотношение сторон, поэтому A0×1.25 и A3×3.54 неразличимы —
  выбирается вариант с масштабом ближе к 1.

Далее координаты нормализуются к PDF-пунктам и переводятся в **проценты** от размера
холста (`use_percent_coords=True`). Если размеры холста определить нельзя, экспорт
переключается на абсолютные координаты и пишет `coordinate-type="absolute"`.

**Координаты — единицы холста редактора, а не пункты листа.** Холст размечен
сеткой 20, и минимальный осмысленный объект — две клетки. Символ устройства

к одному, кружок приезжал радиусом 14 при минимуме 20, и редактор поднимал
его сам — отсюда «размер кружков не тот».

Верхнего предела у координат нет. Размер сцены задаётся блоком `canvas`
элемента `meta`: редактор рисует по нему рамку листа и считает координаты,
заданные процентом, но за рамку выходить не запрещает. Размер хранится
числом, а не форматом бумаги, — один и тот же A3 занимает от 7460 до 16160
единиц, смотря насколько мелко Eplan нарисовал на нём символы. Числа кратны
сетке: крайним элементом обычно оказывается рамка чертежа или надпись,
а они на узлы сажаются, но диагональ с точными координатами край бы сдвинула,
поэтому размер округляется вверх.

**Объекты стоят в узлах сетки, чертёж — нет.** Редактор привязывает
к сетке только то, что двигает человек, и по-разному: текст прыгает на узел
при первом касании, а круг и отрезок едут на целое число клеток, сохраняя
своё смещение навсегда. Схема, пришедшая мимо узлов, разъезжается по мере
работы с ней. Поэтому группы, рамки, кружки и тексты садятся на узлы,
радиус кратен 20 и не меньше 20, а чертёж выровнен мягко: ортогональный
отрезок садится, если это смещает конец не больше чем на полклетки
и не схлопывает его; диагонали и звенья кривых остаются точными.

Что ещё следует из их кода импорта и спецификации:

- **массив обязателен.** Объект импортёр заворачивает в массив из одного
  элемента, и из дерева `PlantGeometry` получается один элемент без типа —
  файл открывается, холст пуст. Это была причина первой неудачной передачи;
- **ключи уникальны, ссылки согласованы.** `parentKey` и `children`
  переводятся по карте старых ключей, и ссылка на отсутствующий элемент
  остаётся битой. Здесь они выводятся из содержимого (`uuid5`);
- **`id` — настоящий `null`, `composition` не отправляется** (в редакторе это
  массив ключей примитивов компонента, а не булево);
- **`states` — ровно одно состояние с пустым `overrides`.** Иначе базовые
  `x/y/w/h` при отрисовке игнорируются. Состояния по операциям уезжают
  своим полем `contur_states`;
- **`color` в редакторе означает заливку**, поэтому смысл линии («red» контур устройства,
  «blue» труба) уехал в `contur_color`;
- **лишние поля доезжают** (`...rest`), поэтому имя устройства, техобъект,
  артикул, связи и состояния едут вместе с элементом.

Что чем рисуется:

| На чертеже | Элемент | Примечание |
|---|---|---|
| сегмент линии | `line` | плюс `contur_color`, `stroke_width` ступенями 1/2/3, `line_id` |
| рамка листа и разлиновка штампа | `line` с `frame: true` | раньше отбрасывалась вместе с живой геометрией |
| **сопоставленное устройство** | **`group` с `contur_device: true`** | цельный объект: внутри прозрачный `rectangle` (держит габарит) и линии его же символа с чертежа в локальных координатах |
| надпись самого чертежа | `text` с `drawing: true` | обозначения Eplan, штамп |
| данные о листе | `meta` | не фигура: `visible: false` |
| рамка техобъекта | `rectangle` с `contour: true` | по `CONTUR_HMI_CONTOURS=1`, цвет в `strokeColor` |
| имя контура, подпись устройства | `text` | по `CONTUR_HMI_CONTOURS=1` и `CONTUR_HMI_LABELS=1`, кегли 16 и 12 |
| техобъект как группа | `group` | по `CONTUR_HMI_GROUPS=1` |

Порядок элементов — это порядок отрисовки: `meta` → чертёж → надписи
чертежа → объекты устройств.

**Разметка по умолчанию не отправляется.** Рамки техобъектов, их имена
и подписи устройств — это выводы конвейера о чертеже, а редактору нужен сам
чертёж и данные: обозначения Eplan и так есть в чертеже отдельными
надписями. Устройство при этом стало цельным объектом, а не кружком-маркером
поверх россыпи отрезков: его можно выделить и подвинуть целиком, и на нём
висит всё, что о нём известно.

**Внутри объекта — готовая фигура библиотеки** (§6.2.3). Раньше
там лежали красные отрезки с чертежа Eplan, и находились они не у всех:
на A0 у 174 объектов из 233. Теперь внутри библиотечный клапан, датчик
или насос, и фигура есть у всех 233.

**Данные, а не только фигуры.** До версии 1.1 в файле была одна геометрия,
а состояния устройств, трубы, связи и операции жили только в XML:

| Что | Где лежит | Сколько на A0 |
|---|---|---|
| **теги устройства**: каналы ввода-вывода с адресом в контроллере | `contur_tags` | у всех сопоставленных |
| положение устройства в каждой операции | `contur_states` | 1911 состояний, 64 операции |
| программы операций | `meta.operations` | 64 |
| поля XML целиком | поля объекта устройства | — |
| принадлежность отрезка трубе | `pipeline_id` у линии | 767 труб |
| соседи устройства по трубам | `connected_devices` | 164 из 233 |
| трубы, связи, точки сопряжения, техобъекты | `meta` | 767 / 250 / 4713 / 24 |
| узлы контроллера и сигналы проекта | `meta.nodes`, `meta.signals` | 7 / 147 |
| уставки, свойства и состав техобъекта | `meta.tech_objects[].lua_objects` | связь через устройства |
| надписи чертежа | `text` с `drawing` | 779 |

Теги до этой правки терялись целиком: сопоставление брало из описания
устройства имя, артикул, категорию и подтип, а `DI`/`DO`/`AI`/`AO` с адресом
(`node`, `offset`, `module_offset`, `physical_port`, `logical_port`), `par`,
`rt_par` и `prop` выбрасывало прямо там же — файл описывал, что нарисовано,
но не к чему это подключено.

Техобъект листа связывается с описанием через свои устройства: имя контура
на чертеже (`LA_TANK1`) и имя объекта в описании («Линия наполнения
ALPMA O») — разные вещи, а состояние устройства несёт идентификатор объекта.

Настройки — переменными окружения: `CONTUR_HMI_SCALE`, `CONTUR_HMI_GRID`,
`CONTUR_HMI_GROUPS`, `CONTUR_HMI_LINES`, `CONTUR_HMI_FRAME`,
`CONTUR_HMI_DEVICES`, `CONTUR_HMI_CONTOURS`, `CONTUR_HMI_LABELS`,
`CONTUR_HMI_TEXTS`, `CONTUR_HMI_STATES`, `CONTUR_HMI_STATE_COLORS`,
`CONTUR_HMI_META`, `CONTUR_HMI_JUNCTIONS`, `CONTUR_HMI_SYMBOLS`,
`CONTUR_HMI_SYMBOL_CELLS`, `CONTUR_HMI_SYMBOL_MAP`, `CONTUR_HMI_TANKS`,
`CONTUR_HMI_TANK_NAMES`, `CONTUR_HMI_AGITATOR_NAMES`.

Контрольный лист A0 даёт 5979 элементов (3586 отрезков чертежа верхним
уровнем, 779 надписей, 233 объекта устройств с их рамками и готовыми
фигурами внутри — 1147 примитивов, `meta`).
Приёмка по списку самопроверки из спецификации импорта выполняется кодом
(`contur/hmi/validate.py`, §6.2.2) и на обоих листах проходит без замечаний;
размер листа печатается справочно (§6.2.3).

#### 6.2.1 Что оказалось не так и почему

Три замечания к первым файлам разобраны до причин.

- **Ромбы вместо кругов** — `polygon` без списка `points`: редактор
  строит в этом случае правильный многоугольник по своему `sides`. Делал
  это режим `CONTUR_HMI_SHAPES=class`, он убран.
- **Размер кружков** — масштаб (см. выше). В старых файлах было хуже:
  `w = h = "5.00%"` у всех устройств, то есть 250×250 после умножения
  на холст.
- **Обрывы линий** — три причины, все на стороне выгрузки: отсечение рамки уносило
  73 отрезка живого чертежа, 784 кривые уезжали хордой (отклонение
  до 6.3 пункта), четыре вырожденных отрезка приезжали точками.

#### 6.2.2 Приёмка выгрузки (`contur/hmi/validate.py`)

Список, по которому редактор принимает файл (§10 спецификации импорта),
выполняется кодом: `hmi_validate` читает готовый файл
с диска и говорит, что в нём не так. Отдельно от экспорта намеренно —
экспорт знает, что он собирался сделать, а проверка знает, чего от файла
ждут на той стороне.

Строгость разная у двух групп, и это их разделение: объекты (группы,
рамки, кружки, тексты) обязаны стоять в узлах сетки, а чертёж мерится
мягче — короткие отрезки и ортогональные вне сетки считаются показателем,
а не поломкой. Запускается и сам по себе:
`python -m contur.hmi.validate выгрузка.json`.

#### 6.2.3 Готовые фигуры библиотеки редактора (`contur/hmi/symbols.py`)

Исходником служит сцена редактора (`MOZARELLA_01_2026-08-21.json`,
формат `SCADA_EDITOR_SCENE`): в ней уже нарисованы клапан, датчик
и ёмкость. Рисовать их заново значит отдавать схему, непохожую на сами
мнемосхемы редактора, поэтому на месте устройства теперь стоит его фигура.

**Каталог.** `tools/extract_symbols.py` читает сцену и находит
повторяющиеся фигуры: кандидат — либо то, что собрано в группу (её собрал
человек, значит фигура законченная), либо одиночная фигура, встречающаяся
не реже трёх раз (иначе в каталог попал бы каждый отрезок чертежа). Дети
группы переводятся в её систему координат, нормируются к габариту
и округляются — получается подпись формы, по которой фигуры и сравниваются.

Две тонкости, без которых каталог выходит неверным:

- **вершины приводятся к общему порядку.** Один и тот же прямоугольник
  нарисован то с левого верхнего угла, то с правого; по списку точек
  это разные фигуры, и 21 клапан распадался на 14 и 7. Замкнутая фигура
  сравнивается по всем сдвигам и обоим направлениям обхода, порядок
  примитивов в подписи не значит ничего;
- **за образец берётся самый частый размер, а не самый крупный.** Кружок
  датчика нарисован радиусом 40 и 60, а рядом стоит обод аппарата
  радиусом 780 — та же форма. По самому крупному символ датчика уехал бы
  в габарит 1560.

Из сцены вынуто четыре фигуры оборудования: `valve` (120×120,
14 экземпляров), `valve_v` (то же стоя, 7), `sensor` (круг r60
с обозначением внутри, 10) и `tank` (160×240, 2). Каталог лежит
в `hmi_symbols.json` рядом с кодом.

Ещё три живут в коде (`hmi_symbols.BUILTIN` и `ALIASES`), потому что
цельной фигурой в сцене их нет: `manual_valve` — «бабочка» из двух их
треугольников, которые стоят вплотную, но группой не оформлены; `pump` —
насос, которого в сцене нет вовсе, и форма взята с чертежа Eplan (круг,
вписанный треугольник остриём по потоку, горизонтальный диаметр, все
вершины на круге); `agitator` — мешалка, которая заимствует фигуру
датчика, потому что Eplan рисует её тем же кружком с обозначением.
У последних двух стоит `origin: "contur"`: это всё, что нарисовано
не ими. Каталог перекрывает встроенные по имени — пришлют свой насос,
подставится он.

**Выбор фигуры** — по обозначению устройства (`DEFAULT_DEVICE_SYMBOLS`,
поправки через `CONTUR_HMI_SYMBOL_MAP`). Два правила сверх карты:

- клапан **без имени в Lua** — ручной: у него нет ни одного канала
  ввода-вывода, контроллер про него не знает, и рисуется он «бабочкой»;
- клапан **стоячий**, если кластер красных линий устройства вытянут
  по вертикали больше чем на четверть: в библиотеке клапан нарисован в двух видах;
- **мешалка вместо насоса**, если в описании из Lua есть «мешал»
  (`CONTUR_HMI_AGITATOR_NAMES`). Обозначение `M` носят и насосы, и мешалки,
  а Eplan рисует их по-разному: насос стоит на трубе кругом с рабочим
  колесом, мешалка — кружок с обозначением плюс лопасть в самом танке.
  На A0 из пятнадцати `M` восемь мешалки, и все восемь приезжали насосом.
  Своей приметы в чертеже у мешалки нет, различить можно только по описанию.

**Размер сменил масштаб всего листа.** Библиотечная фигура нарисована на десяти
клетках (200 при сетке 20), а лист растягивался под кружок в две.
Теперь `k = 200 / обычный символ листа` (A0 — 6.39, лист 13 mozzarella —
6.49), и множитель каталога выходит единицей: фигура приезжает точь-в-точь
как нарисована, все её узлы совпадают с сеткой холста. Множитель один
на весь каталог, а не «вписать в габарит устройства»: иначе «бабочка» 80×40,
вписанная в квадрат клапана, стала бы в полтора раза крупнее, чем её рисуют.

Побочный итог — лист стал крупным: A0 занимает 21520×15240. Ужимать его
некуда и незачем: предела координатам у редактора нет, а фигура при этом
вырождается — в две клетки круг привода уходит в радиус 7 при минимуме 20.
Размер меняется числом `CONTUR_HMI_SYMBOL_CELLS`: 10 клеток — 21520×15240,
6 — 12920×9160, 3 — 6480×4580, 2 — 4340×3060 (фигуры уже не разобрать).

**Сетка внутри фигуры.** При десяти клетках множитель единица, и все
примитивы стоят в узлах. При меньшем размере узлы делятся — половина
клетки при трёх, треть при двух, — и требовать от них сетки нельзя:
это значило бы перерисовать саму фигуру. Примитивы помечены
`contur_symbol_part: true`, и приёмка считает их третьим уровнем строгости,
рядом с чертежом. В узлах обязана стоять оправа — группа устройства
и её рамка.

**Красные линии устройства, получившего фигуру, не отправляются вовсе** —
ни детьми группы, ни верхним уровнем: иначе символ Eplan просвечивал бы
сквозь библиотечный клапан. Символы Eplan внутри устройств — это было 2367 красных
отрезков на A0; вместо них теперь 1084 примитива каталога, и файл похудел
с 8287 элементов до 7004. Сам чертёж не изменился: 4674 отрезка верхним
уровнем как было, так и осталось.

**Подмена на библиотечный компонент.** У группы стоит `contur_symbol` —
имя фигуры, `contur_symbol_size` — её собственный габарит,
`contur_symbol_origin` — откуда она. Увидев эти поля, редактор вправе
выбросить детей с `contur_symbol_part` и поставить свой компонент в габарит
группы. Данные устройства лежат на самой группе и подмены не замечают.
Готовой библиотеки в редакторе пока нет, поэтому фигура едет и геометрией тоже: файл работает уже сейчас,
а подмена появится, когда появится.

**Ёмкость техобъекта** (`_tank`) — техобъект, похожий на ёмкость по имени
(`TANK`, `БАК`, `COAG`, `CIP`…, список в `CONTUR_HMI_TANK_NAMES`),
рисуется фигурой `tank` по границам своего контура. Растягивается не всё
подряд: деталь, занимающая вдоль оси больше 60% символа (корпус, полки
внутри), тянется вместе с ним, а мелкая сохраняет свой размер и только
переезжает пропорционально. Без этого патрубок шириной в клетку
на техобъекте 3880×3040 раздувался до полутысячи. Появляются ёмкости
только там, где чертежа в файле нет (`CONTUR_HMI_TANKS=auto`): с чертежом
аппарат нарисован дважды — у `LA_TANK1` на листе 13 корпус и уровень
жидкости рисует сам Eplan.

### 6.3 `PlantGeometry` JSON, версия 1.3 (`json_export.py`) — состав целиком

Формат выбирается расширением файла (`exporters.py`): `Ctrl+E` предлагает
`*.json` (редактор), `*.xml` и `*.plant.json`; пакетная обработка —
`--format xml|json|plant-json|both`. Редактор мнемосхем этот формат не
понимает — он для потребителя, которому нужны трубы, связи и разметка целиком.
Состав тот же, что у XML, различается запись:

```json
{

  "version": "1.3",
  "coordinate_type": "percent",
  "original_svg_coord_system": "scaled_1.25",
  "canvas": { "width": 3368.0, "height": 2384.0, "units": "pt" },
  "current_operation": { "id": "…", "name": "…", "tech_object": "…",
                         "devices_opened": 0, "devices_closed": 0, "devices_total": 0 },
  "tech_objects": [
    { "name": "CW_TANK1",
      "contour": { "name": "CW_TANK1", "tech_object": "CW_TANK1",
                   "bounds": [62.064, 51.348, 73.999, 68.241],
                   "center": [68.032, 59.795], "width": 11.935, "height": 16.893 },

          "descr": "Нижний уровень", "article": "IFM.LMT121",
          "operation_state": "не используется" } ] } ],
  "junction_points": [ { "x": 0.0, "y": 0.0, "red_line_id": 12, "blue_line_id": 87,
                         "red_device": "V7", "confidence": 1.0 } ],
  "pipelines": [ { "id": 1, "name": "pipeline10201", "segment_count": 7,
                   "total_length": 123.45, "connected_devices": ["V7", "V8"],
                   "segments": [ { "id": 1, "x1": 0.0, "y1": 0.0, "x2": 0.0, "y2": 0.0 } ] } ],

  "svg": "<svg …размеченный лист одной строкой…>"

Отличия от XML только в записи, не в составе:

- числа остаются числами, а не строками `"62.064%"`; единицы называет
  `coordinate_type` (`percent` — доля холста в процентах, `absolute` — пункты PDF);
- границы и центры — массивы вместо строк через запятую;
- счётчики `count` не дублируются: длина массива и есть счётчик;
- разметка лежит строкой в `"svg"`, а не в CDATA секции `SVGContent`;
- `ensure_ascii=False` — описания устройств читаются глазами.

Сцену (координаты, точки сопряжения, трубы) для обоих форматов собирает
`contur/scene.py`, `build_scene()`: раньше этот блок был скопирован в `xml_export`
и `postgreSQL_export`, третья копия означала бы, что каналы выдачи расходятся
в данных об одном и том же листе. Совпадение сверяется на настоящем листе
в `check_pipeline` (шаг «JSON описывает тот же лист») и на синтетическом —
в `tests/test_json_export.py`.

Файл самодостаточен и потому крупный: на контрольном листе A0 — 2.4 МБ против
2.6 МБ у XML, из них 1.1 МБ приходится на разметку в поле `"svg"`.

Обратное чтение JSON приложением пока не сделано: `Ctrl+Shift+X` открывает
только XML (`contur/export/xml_reader.py`).

### 6.4 `matched_devices.xml`, версия 1.0 (`device_matcher.generate_output_xml`)
Урезанный формат без SVG/труб/точек, координаты **абсолютные** в PDF-пунктах.
Пишется при запуске `device_matcher.py` как самостоятельного скрипта.

### 6.5 PostgreSQL (`postgreSQL_export.py`, БД по умолчанию `hmi_design`)
| Таблица | Ключевые поля |
|---|---|
| `contours` | `name` (UNIQUE), `tech_object_name`, `bounds_*`, `center_*`, `width`, `height` |
| `devices` | `contour_id → contours`, `lua_name` (UNIQUE), `pdf_name`, `device_type`, `article`, `description`, `coord_x/y`, `confidence`, `operation_state`, `operation_step` |
| `connections` | трубопроводы: `name`, `total_length`, `segment_count`, `connected_devices` |
| `junction_points` | `x`, `y`, `red_line_id`, `blue_line_id`, `red_device_name`, `contour_id` |

Координаты хранятся **строками** (`VARCHAR`), т.к. содержат `%`. Таблицы создаются автоматически
(`auto_create_tables=True`), есть `drop_tables()` для отладки.

### Пакетная обработка страниц

Приложение работает с одной страницей за раз; для файла из 265 страниц это
265 ручных прогонов. `batch_process.py` прогоняет тот же конвейер по всем
страницам подряд:

```powershell
python batch_process.py --pdf схема.pdf                  # все страницы
python batch_process.py --pdf схема.pdf --pages 1-20     # только часть
python batch_process.py --pdf схема.pdf --no-markup      # обследование покрытия
python batch_process.py --pdf схема.pdf --format json    # в формате редактора мнемосхем
```

На каждую страницу получаются `page_NNN.xml`, `page_NNN_marked.svg`
и `page_NNN_geometry.xml`, плюс `summary.json` с показателями по страницам
и `coverage.json` — какие устройства Lua встретились на чертежах, а какие нет.

`--format json` даёт `page_NNN.json` в формате редактора мнемосхем (§6.2),
`--format plant-json` — `page_NNN.plant.json` (§6.3), `--format both` — xml и json
сразу; `both` стоит примерно вдвое дороже, потому что разметка разбирается
для каждого формата заново.

Флаг `--no-markup` пропускает разметку YOLO и экспорт: сопоставление от них
не зависит, поэтому обследование покрытия по 265 страницам занимает 5 минут
вместо нескольких часов.

Разметка кэшируется, поэтому повторный запуск доделывает прерванную работу:
страница, посчитанная за 166 с, при повторе занимает 3 с.
```

**Порядок работы в GUI:**
1. «Загрузить Lua файлы (devices)» → `main.io.lua` / `main.wago.lua`;
2. «Загрузить Lua файлы (main objects)» → `main.objects.lua`;
3. «Загрузить входной PDF» — для многостраничного файла спросит номер страницы,
   затем запустит извлечение геометрии и сопоставление;
4. «Разметить входной PDF (YOLO)» → получаем SVG-подложку (обязателен для экспорта);
5. выбрать операцию в нижней панели (опционально — попадёт в XML как состояние устройств);
6. «Экспорт в XML» и/или «Экспорт в PostgreSQL».

**Зависимости** — в `CONTUR/requirements.txt`: `PySide6`, `PyMuPDF` (`import fitz`), `lupa`,
`ultralytics` + `torch`, `opencv-python`, `numpy`, `svgwrite`, `psycopg2-binary`.

```powershell

- `ultralytics` подтягивается вместе с конфигами и подмодулями (статический анализ их не находит).

### Осталось

1. **Реквизиты БД вводятся вручную** каждый раз; значения по умолчанию берутся из
   `config.DB_CONFIG`, но пароль не сохраняется (и не должен — нужен отдельный способ хранения).
2. **`parse_lua.py` исполняет Lua-код** через lupa: сторонний файл выполняется как есть.
   Для доверенных выгрузок EPlanner приемлемо, но это остаётся точкой риска.
3. **Эвристика масштаба неоднозначна без `pdf_size`.** Если экспорт запускается на SVG
   без исходного PDF, A0×1.25 неотличим от A3×3.54 — берётся масштаб ближе к 1.
4. **Детекция YOLO упирается в CPU** (на этой машине 2 потока, ~0.28 с на плитку,
   ~30 с на лист A0). Ускорит только GPU или модель поменьше.
5. **Пропуск пустых плиток ничего не дал** на плотных схемах — там непустая каждая плитка.
   Оптимизация останется полезной для разреженных чертежей.
6. **`objects_loader` — глобальный синглтон** `objects_data`; при работе с несколькими
   проектами в одном запуске состояние будет общим.
7. **Покрытие проверками частичное**: `check_pipeline.py` прогоняет конвейер и проверяет
   ключевые инварианты, но это не модульные тесты.
8. **12 устройств из Lua не находятся на тестовой схеме** (`M1V91`, `M1V92`, … `M6V92`) —
   отчёт их показывает, но причина не разобрана: либо подписи вне контура, либо их
   действительно нет на этом листе.
9. **Кривые упрощаются до хорды** и при генерации SVG, и при разборе. Для скруглений
   трубопровода этого достаточно, но геометрия дуги теряется.
10. **Идентификаторы объектов изменились** (`[ 2 ]_[ 4 ]` → `2_4`) после перехода на lupa.
    XML, выгруженные раньше, ссылаются на старый вид.
11. **112 устройств из 279 не опознаются по подписи.** Модель их находит, но метки
    рядом нет либо она досталась соседу. Это главный оставшийся источник потерь —
    больше, чем что-либо в геометрии.
12. **Модель различает только три класса** (`valve`, `sensor`, `pump`). Мешалок среди
    них нет, поэтому `TANKxM1` помечаются как расхождение класса и подписи. Это
    ограничение модели, а не ошибка привязки.
13. **Подгонка масштаба детекции почти не окупается.** Доведение относительного
    размера символа до обучающего даёт +10 уверенных детекций при пятикратном
    росте времени; выигрыш только в чистоте (сомнительных 30 → 12).

## 9. Контроль версий и откат

Исходное состояние помечено тегом **`baseline`**, каждое изменение — отдельным
коммитом, поэтому откатить можно как всё сразу, так и одну правку.

Не в репозитории (см. `.gitignore`): `.venv/`, `*.rar`, `*.zip`, `output/`, `runs/`
кроме используемой модели, и папка `doc` с исходными материалами.
Для репозитория выставлен `core.autocrlf false`, чтобы Lua-файлы не меняли переводы строк.

```powershell
git log --oneline                  # список изменений
git show <хеш>                     # что именно поменялось
git diff baseline --stat           # всё, что изменилось с исходного состояния

git checkout -- CONTUR\xml_export.py   # откатить незакоммиченные правки файла
git revert <хеш>                       # отменить один коммит, сохранив историю
git checkout baseline -- CONTUR\       # вернуть весь код к исходному состоянию
git reset --hard baseline              # полностью откатиться (незакоммиченное пропадёт)
```

После любого отката имеет смысл прогнать `python check_pipeline.py` — он покажет,
что конвейер цел.

## 10. Глоссарий

| Термин | Значение |
|---|---|
| **tech_object** / техобъект | Единица технологии: танк, линия, сыроизготовитель (`LA_TANK1`, `COAG1`, `O7`). В Lua — `name_eplan` / `name_BC` |
| **mode / операция** | Режим работы техобъекта (`Мойка`, `Выдача`). В `main.objects.lua` — `modes` |
| **state / состояние** | Фаза операции; содержит `opened_devices`, `closed_devices`, `devices_data`, `DI_DO`, `steps` |
| **step / шаг** | Шаг внутри состояния: какие устройства открыть/закрыть, `time_param_n`, `next_step_n`, `jump_if` |
| **device** | Физическое устройство: клапан `V`, мотор `M`, датчики `LS/LT/TE/QT/FQT/PT/PC`, дискретные/аналоговые `DI/DO/AI/AO` |
| **subtype / dtype** | Классификация устройства в Lua (напр. `subtype=13` → `V_IOLINK_VTUG_DO1_FB_OFF`) |
| **node / IO-узел** | Узел ввода-вывода (`A100`, `AXL F BK ETH`) с IP и списком модулей |
| **contour / контур** | Замкнутая пунктирная область на PDF, очерчивающая техобъект |
| **junction point** | Точка стыка красной (устройство) и синей (труба) линии в размеченном SVG |
| **pipeline** | Связная цепочка синих сегментов = трубопровод |
| **PAC** | Контроллер (`PAC_name = 'O1-Моцарелла'`, `PAC_id`) |
