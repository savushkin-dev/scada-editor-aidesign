# CONTUR — короткая сводка

> Одна страница вместо чтения всего `PROJECT.md` (50 КБ). Здесь только то, что нужно,
> чтобы вспомнить состояние дел и продолжить. Подробности — в `PROJECT.md`,
> история решений — в `git log --oneline baseline..HEAD`.
> Обновлено: 2026-08-24 (покрытие 244 устройства из 245 и 145 сигналов из 147;
> выгрузка для редактора: на месте устройства стоит готовая фигура
> библиотеки, вынутая из сцены редактора).

## Что это

PDF-схема Eplan + Lua-описание контроллера → сопоставление устройств → JSON для
редактора мнемосхем (а также XML и PostgreSQL). Код в `CONTUR/`, точка входа
`xml_viewer.py`.

## Запуск

```powershell
cd <папка модуля>
python xml_viewer.py                                  # приложение (запуск 0.5 с)
python check_pipeline.py --svg <размеченный.svg> --report   # проверка + тесты + отчёты
python tests/test_ui_state.py                         # только проверки интерфейса (85 шт.)
python tests/test_details_panel.py                    # панель сведений (31 шт.)
python tests/test_navigation.py                       # движение по схеме (17 шт.)
python tests/test_lua_shared.py                       # обмен с соседними контроллерами (7 шт.)
python tests/test_device_dossier.py                    # досье устройства (9 шт.)
python batch_process.py --pdf схема.pdf --pages 1-20  # пакетно по страницам
python batch_process.py --pdf схема.pdf --format json # страницы в формате редактора
python batch_process.py --pdf схема.pdf --no-markup   # покрытие по всему файлу
python tools/calibrate_scale.py                       # подбор параметров детекции
python tools/extract_symbols.py --scene сцена.json --list   # готовые фигуры в сцене
python tools/extract_symbols.py --scene сцена.json --name 2=valve   # собрать каталог
pyinstaller МоеПриложение.spec --noconfirm            # сборка .exe (~10 мин, 2.2 ГБ)
```

`.venv` нерабочее (создано от другого пользователя) — запускать системным Python 3.11.

Размеченный SVG для `--svg` заново делать не нужно: он лежит в кэше
(`output/markup_cache/*.svg`), и его sha256 совпадает с `разметка_sha256`
в эталоне — по этому хешу и находится нужный файл. Разметка стоит ~80 секунд,
поиск в кэше — секунду.

| | |
|---|---|
| Перемещение | тянуть схему левой кнопкой, зажатым колесом или пробел+ЛКМ; стрелки (Shift — крупнее) |

| Поиск устройства | `Ctrl+F`; щелчок в дереве подсвечивает, двойной приближает |
| Панель сведений | щелчок по устройству на схеме, в каталоге или по операции внизу; «Сбросить» или `Ctrl+Shift+D` — очистить |

Настройки, размеры окна, последние папки и файлы запоминаются между запусками.

## Сделано

**Исправленные ошибки** — координаты экспорта уезжали в 1.25 раза; свой же XML не
открывался (`float("62.064%")`); проценты доходили до 1178%; связи «устройство ↔ труба»
не работали вовсе (`data-device-name` не писался); кривые в SVG не разбирались
(запятая вместо пробела); разметка в GUI теряла 54% линий (`svgwrite` отвергал
нестандартный атрибут); самописный парсер Lua портил `devices_data`; выключенные
подсказки отнимали выбор устройства (на сцену ложился простой эллипс вместо
`DeviceGraphicsItem`, а подсветка и показ под курсором ищут именно его).

**Порядок «сначала PDF, потом Lua» заходил в тупик** — каталог устройств
оставался пустым, на схеме нечего было выделить, хотя разметка проходила
и красила устройства. Сопоставление вызывалось только из
`_on_geometry_finished`, а извлечение геометрии — только из `_open_pdf`,
и разбор Lua ни то, ни другое не начинал. Если Lua ещё нет, `_open_pdf`
предлагает загрузить их и выходит, не начав геометрию; если рядом лежит
старый `output/parsed_lua.json` от прошлого проекта, вопроса нет вовсе —
сопоставление отрабатывает по чужим данным, даёт ноль и больше никогда
не пересчитывается. Теперь разбор Lua продолжает конвейер с того места,
где тот остановился (`_continue_after_lua`), а пересобрать каталог можно
и вручную — «Обработка → Сопоставить устройства», `Ctrl+Shift+M`.

**Устройство ничего не рисует поверх чертежа, пока его не тронули** —
закрашенный кружок, а после него постоянная обводка ложились поверх символа
Eplan и прятали ровно то, на что человек смотрит. Теперь на сцене лежит
невидимый прямоугольник по габариту устройства: он только ловит курсор
и щелчок. Обводка — ребёнок этого прямоугольника, повторяет линии символа
с чертежа и показывается лишь под курсором или у выбранного в каталоге
устройства.

Габарит и линии приходят от разметки: `view_size` — габарит кластера красных
линий, `view_shape` — сами линии относительно центра. До разметки ни того,
ни другого нет: габарит берётся запасной, обводка идёт по нему же, иначе
наводить курсор было бы не на что.

Оба поля живут отдельно от `extra_data`: его экспортёры перебирают целиком,
и обводка уехала бы в файл редактора. Проверки на все три выгрузки это
держат. Заливка прямоугольника прозрачная, но она есть: с `Qt.NoBrush`
`shape()` сжимается до штриха пера, и попасть по устройству курсором можно
было бы только точно по линии.

Цвет — `CONTUR_DEVICE_OUTLINE`, толщина `CONTUR_DEVICE_OUTLINE_WIDTH`
в пикселях экрана, чтобы обводка не поедала схему на увеличении. По умолчанию
белый, и на белом листе он не читается: обводка ложится ровно на красные
линии символа и вместо подсветки их стирает. Контрастный цвет
(`CONTUR_DEVICE_OUTLINE=#00b0ff`) виден сразу — решение за тем, кто смотрит.

Красить устройства по типу окно перестало: разбивка по типам осталась
в легенде, цвета в выгрузке прежние.

**Досье устройства: всё известное — при самом устройстве**
(`device_dossier.py`). Часть сведений жила при устройстве (описание, артикул,
теги — каналы ввода-вывода с адресом, уставки, обмен), а часть добывалась
заново каждым, кому она понадобилась: панель спрашивала описание объектов
при каждом щелчке, выгрузка считала то же самое в момент записи файла,
а поле состояний в модели устройства так и оставалось пустым — его никто
не заполнял. Три источника одного и того же — три способа разойтись.

Теперь после сопоставления за устройством закрепляются **состояния**
(где оно открывается и закрывается: операция, состояние, шаг, что с ним
происходит — 1911 записей на 233 устройства контрольного листа),
**техобъект целиком** (уставки, свойства, состав оборудования, системные
параметры) и **соседи по трубопроводам** — эти появляются после разметки,
когда есть трубы. Панель и выгрузки читают закреплённое и физически
не могут показать разное; поиск техобъекта с номером и без переехал
в один модуль из двух.

Снимок, а не ссылка: устройство самодостаточно. Плата — снимок устаревает,
если перезагрузить описание объектов, поэтому окно пересобирает досье после
каждой загрузки `main.objects.lua`, а сборка дёшева.

**Попутно нашлась дыра: пакетная выгрузка теряла состояния целиком.**
`batch_process` разбирал `main.objects.lua` ради имён объектов, но
не загружал его в `objects_data`, и каждая страница уезжала без
`contur_states` — ноль у всех 233 устройств контрольного листа, хотя тот же
лист через окно давал 1911. Теперь описание загружается, и пакетный прогон
даёт те же 1911. Все выгрузки, сделанные пакетно до этого дня, состояний
не несут — их нужно пересобрать.

**Сигналы обмена с соседями перестали числиться пропажами**
(`parse_lua_shared.py`). Сигнал `LINE2DI501` в `main.io.lua` выглядит как
обычный канал ввода-вывода, и по нему не видно, что это не датчик проекта,
а строка обмена с чужим контроллером. Отчёт отсеивал такие имена косвенно —
«сопоставился ли на этом листе хоть один сигнал», — а на мнемосхеме про них
нельзя было сказать ничего.

Рядом с `main.io.lua` у проекта станции мойки лежит `shared.lua`, и там это
написано прямо: три соседних контроллера с адресом и номером станции Modbus,
под каждым — что у него читается и что ему пишется. Всего 146 сигналов, и все
146 нашлись среди устройств `main.io.lua`. На листе 5 из тридцати четырёх
«пропаж» тридцать оказались обменом: семнадцать с молокохранилищем,
тринадцать с сырыми сливками.

Читается файл настоящим Lua, как и остальные, но с одной хитростью: имена
сигналов в нём — необъявленные глобальные (`__LINE2DI501`), и при обычном
выполнении список выходит пустым, потому что в Lua необъявленное имя это
`nil`. Перед выполнением на `_G` вешается метатаблица, возвращающая само имя.
Из-за неё же нельзя спрашивать «есть ли таблица `remote_gateways`» обычным
способом — метатаблица ответит «есть» на что угодно, поэтому спрашивается
`rawget`.

Обмен уезжает вместе с тегами устройства (`contur_tags.exchange`) и виден
в панели сведений отдельным разделом: контроллер, направление, адрес,
станция. Файл необязательный: у молокохранилища и моцареллы его нет вовсе,
и без него всё работает ровно как раньше.

**Кнопка, лампа, сирена и колонна — нарисованы отдельно.** Библиотека
редактора про технологию: клапаны, насосы, датчики, теплообменники.
Электрических устройств в ней нет вовсе, и на месте лампы или кнопки
в объекте оставалась пустая рамка — на приёмке это выглядит как потеря,
хотя это отсутствие исходника.

Лампа и кнопка срисованы с чертежа: на листе 240 лампа — кружок с косым
крестом и выводами `x1`/`x2`, кнопка (`-SB2`) — контакт с толкателем.
Сирены и колонны как рисунка в чертеже нет: Eplan показывает их клеммным
блоком с подписями «Supply GND» и «Supply +» (лист 56), из такого символа
мнемосхему не сделать, — эти две нарисованы по общепринятому виду, рупор
со звуковыми дугами и две секции под куполом.

Рисует их генератор (`tools/make_contur_symbols.py`), а не рука: дуги
и крест считаются, ключи выводятся из содержимого, файл при каждом запуске
получается один и тот же. Пишется он в формате сцены редактора
(`CONTUR_extra_components.json`) — то есть это одновременно исходник фигур
и готовая к передаче сцена. Собирается в каталог тем же ключом, что
библиотека, только с пометкой о происхождении (`--origin contur`):
по ней видно, что фигуру стоит заменить библиотечной.

В каталоге стало 53 фигуры, из них 4 нарисованы здесь. Обозначения `HL`, `SB`, `HA`
и `HLA` перестали быть пустой рамкой; на контрольном листе и на листе 13
моцареллы таких устройств нет, поэтому эталоны не изменились.

**Размер решён: фигура в десять клеток, предела холста нет.** Число 5000,
вокруг которого считались варианты, разобрано до конца: предела
не существует вовсе. 5000 в редакторе — это
протяжённость нарисованной сетки (рисуется она вообще 10000×10000), длина
направляющих при перетаскивании и база для процентных координат импорта.
Клампа позиций нет, камера не ограничена, холст Konva аллоцируется
по видимой области, а не по миру. Выгрузка на 6360×5820 никогда ничего
не нарушала.

Отсюда `CONTUR_HMI_SYMBOL_CELLS` стал десяткой: библиотечная фигура
нарисована на 200 единицах, множитель каталога выходит единицей, и фигура
приезжает точь-в-точь как нарисована — все узлы на сетке 20. Контрольный
лист стал 21520×15240 (встречный расчёт — 21520×15220), лист 13
моцареллы 15480×10940, обычный технологический A3 — около 11900×8400.
Побочно подтянулся чертёж: отрезков короче клетки 407 → 101, потому что
лист крупнее.

Приёмка перестала считать размер листа замечанием — он остаётся в отчёте
числом. Раньше проверка шла от «мира 5000×5000» из спецификации, и лист
A0 стоял красным всегда; теперь красное означает настоящую поломку. Нижняя
граница зума опущена с 0.2 до 0.05, чтобы целиком открывался любой
формат.

Библиотека со временем соберётся в компоненты (примитивы уедут
в `composition`, устройство в дереве станет одной строкой) — со стороны
выгрузки для этого ничего не требуется; у элемента появилось необязательное
поле `zIndex`, он не отправляется, порядок по-прежнему задаётся порядком
массивов.

**Лист A3 прогнан в формат редактора — впервые не по одному листу.**
До сих пор выгружались только контрольный A0 и лист 13 моцареллы, а в проекте
239 листов A3 из 265 (у станции мойки — все 154). Прогнали 24 листа подряд
(`batch_process --format json`, по 10 секунд на лист) и померили, что выходит.

Сцена оказалась вдвое больше расчётной: **7160×5060 вместо 4560×3230**.
Размер сцены зависит не от формата листа, а от того, насколько мелко Eplan
нарисовал на нём символы: на листах A3 одного проекта обычный символ гуляет
от 14 до 32 пунктов, и во столько же раз расходится масштаб. Обмен сигналами —
32 пт и 4480×3180, технологические — 19–20 пт и 7160×5060, плотные
сигнальные — 14.8 пт и 9700×6880.

Технологических листов из 24 — пятнадцать, и держатся они кучно: медиана
7160×5060, максимум 7380×5220 (при прежней фигуре в шесть клеток). Приёмка
по спецификации чистая на 17 листах из 20, и все три замечания — ровно
«схема не влезает в холст».

**Проект станции мойки прогнан целиком** — 154 листа за 626 секунд. Сценой
стали 73 листа, из них 64 с оборудованием; остальные щитовые и клеммные,
сопоставлять там нечего, и пропускаются они за 0.2 секунды. Холст сцены при
фигуре в десять клеток: медиана 9160×6480, размах 7220…17740 — и упирается
он не в формат листа, а в то, насколько мелко на нём нарисованы символы
(13.4…33.1 пункта). Вес сцены: медиана 471 элемент, но на трёх листах
по 15 000 при двух-четырёх устройствах — это плотные чертёжные листы,
мнемосхемы из них никакой.

Заодно выяснилось, что **листы обмена сигналами мнемосхемой не являются**:
там нет приборов, только стрелки «Молокохранилище → Пост №11» с подписями
(«Запрос мойки», «Мойка готова») и блоки `WATCHDOG`. Устройства на них
одни сигналы (`DI`/`DO`/`AI`/`AO`), фигуры им не полагается, и в сцены такие
листы отдавать незачем. Из 24 листов таких пять.

**Библиотека фигур редактора — 31 фигура вместо одной
на всё.** Раньше каталог знал один клапан (`valve`), кружок датчика и ёмкость
из рабочей сцены, а насос был нарисован по чертежу Eplan: цельной
фигуры насоса в той сцене не было. Теперь есть библиотека шаблонов
(`MCA_1_components.json`), где у каждой группы стоит подпись,
и `tools/extract_symbols.py --from-labels` собирает каталог сам: имя берётся
из таблицы `LIBRARY_NAMES`, библиотечная подпись остаётся в фигуре полем `title`
и уезжает на устройство (`contur_symbol_title`) — по ней видно, что
подставлено, не сверяясь с каталогом.

В каталоге 49 фигур: 4 прежние, 31 из библиотеки и 14 собраны поворотом.
Второй вид (`_v`) нужен потому, что клапан на чертеже стоит и вдоль трубы,
и поперёк, а в библиотеке нарисован один раз. Какой вид библиотечный, видно
по самой фигуре: клапан с приводом выше, чем шире, — это стоячий, лежачий
получается поворотом. Признак тот же, по которому выгрузка выбирает вид
у скопления красных линий на чертеже.

Раскладка по обозначениям: `V` — «Санитарная запорная заслонка
с пневмоприводом, НЗ», `VC` — «Санитарный регулирующий клапан», `M` —
«Насос центробежный» (мешалка по-прежнему отличается по описанию из Lua),
клапан без имени в Lua — библиотечный «Клапан с ручным приводом» вместо
прежней «бабочки». У сигнализатора уровня в библиотеке три фигуры — верхний,
средний и нижний, — а обозначение у всех `LS`: различает их описание
(`CONTUR_HMI_LEVEL_NAMES`). На контрольном листе это 88 стоячих заслонок,
78 лежачих, 36 датчиков, 8 мешалок, 16 сигнализаторов уровня и 7 насосов;
на листе 13 моцареллы — 23 заслонки, 6 датчиков, 3 насоса, 2 уровня
и мешалка. Элементов стало 5979 вместо 5916: фигуры библиотеки подробнее
прежних.

Размер устройства перестал быть зашитым числом. Прежние фигуры нарисованы
в габарите 120x120, библиотечные крупнее — заслонка 200x160, — и от прежнего
числа устройство стало бы в полтора раза больше своего места на чертеже:
27 налезающих друг на друга пар вместо 19. Теперь множитель каталога
считается от той фигуры, которой рисуется отсечной клапан
(`hmi_symbols.native_device_size`), и устройство занимает ровно столько же,
сколько занимало. Побочное следствие для вопроса о холсте: единица множителя
теперь приходится не на шесть клеток, а на десять — `CONTUR_HMI_SYMBOL_CELLS=10`
даёт фигуру точь-в-точь их, со всеми узлами на сетке, ценой листа
21520x15240 вместо 12920x9160.

Чего в библиотеке нет: мешалки (заимствует кружок датчика, как и раньше),
кнопки, лампы и сирены. Ёмкость осталась из прежней сцены.

**Круг устройства перестал приезжать дважды.** Имя устройства генератор
разметки пишет и на кривых, а разбор геометрии читал его только у прямых:
круг датчика нарисован четырьмя кривыми Безье, и все четыре уходили
безымянными. Для устройства с круглым символом это значило «геометрии нет
вовсе» — на листе 13 моцареллы так теряли всё у LS1, LS2, LT1, PT1, QT1, TE1
и NY1, а у FQT1, M1, M2, M3 и PC1 оставались одни прямые отводы.

Теперь имя читается и с кривой, а изогнутый примитив разворачивается в свою
ломаную (`svg_geometry._local_shape`): у круга четыре хорды дали бы ромб.
Видно это в трёх местах. Обводка в окне обводит круг, а не пустое место.
Кластер устройства знает свои линии — связей в графе стало 260 вместо 250
(на моцарелле 15 вместо 10). И в выгрузке для редактора символ с чертежа
больше не просвечивает сквозь готовую фигуру: 1088 звеньев кривых ушли
из чертежа к своим устройствам, элементов стало 5916 вместо 7004
(на моцарелле 1366 вместо 1655). Оба эталона обновлены на эти числа.

**Панель сведений, одна на всё** (`details_panel.py`) — справа от схемы.
Щелчок по устройству на схеме или по строке в каталоге показывает всё, что
о нём известно: сводка, параметры, состояния и шаги, сигналы, свойства.
Щелчок по операции внизу показывает в той же панели операцию: сводка,
уставки объекта, её состояния и шаги с устройствами на каждом, свойства.

Раньше про устройство было видно ровно то, что помещалось в подсказку под
курсором, — имя, объект, описание, артикул; каналы контроллера с адресом,
уставки объекта и шаги операций, где клапан открывается и закрывается,
лежали в данных и уезжали в выгрузку, но посмотреть на них самим было негде.

Панелей с вкладками «Параметры / Состояния и шаги / Свойства / Информация»
какое-то время было две: своя у браузера операций и общая справа. Половина
данных не показывалась ни в одной, а искать приходилось в обеих. Осталась
одна: `OperationDetailsWidget` убран (−178 строк), браузер операций стал
списком и только шлёт сигнал о выборе.

Панель — инструмент окна: она ничего не пишет ни в данные, ни в выгрузки,
а читает те же поля, что уезжают редактору (`export_scene`,
`objects_loader`), и показывает их человеку. Тип устройства расшифрован
словами (`config.DEVICE_TYPE_NAMES`): имя `BRINE_TANK1V1`
само по себе не говорит, клапан это или лампа.

Показываемое всегда одно: `show_device` и `show_operation` очищают содержимое
перед заполнением, поэтому данные двух устройств (или устройства и операции)
не накладываются, даже если выбирать их подряд. Сброс — кнопка «Сбросить»
или `Ctrl+Shift+D`; щелчок мимо устройства выбор не снимает, потому что это
ещё и первая половина двойного щелчка, которым схему вписывают в окно.
Каталог мог смениться целиком (другой лист, новое сопоставление) — тогда
перерисовка закрывает панель сама, иначе в ней осталось бы устройство,
которого на схеме нет. Выбор операции панель не отменяет: она красит
устройства по их положению, и это не то же самое, что показ в панели.

Что операция делает с устройствами, берётся тем же индексом, которым
устройство отвечает, где оно участвует (`get_operation_device_states` рядом
с `get_device_states`): показать разное про одно и то же панель не может.
Скелет — состояния и шаги самой операции, поэтому шаг без устройств тоже
виден.

Техобъект устройства ищется и с номером: в описании объект зовут
`BRINE_TANK`, а номер лежит отдельным полем, тогда как на чертеже и в имени
устройства они вместе (`BRINE_TANK1V1` → объект `BRINE_TANK1`). Без этого
объект не находился бы почти никогда — а с ним в панель приезжают его
уставки, свойства и состав оборудования.

**Движение по схеме чинилось трижды и починено только теперь.** Увеличение
колесом уезжало не туда, куда показывает курсор, а к центру схемы, и на
вписанном листе вид вообще не сдвигался с места. Причин было две, и обе
старые.

Точку под курсором возвращали переносом в матрице вида (`translate`),
а QGraphicsView считает перенос делом полос прокрутки и матричный попросту
не применяет. Теперь после масштабирования вид доводится `centerOn` —
прокруткой, и точка под курсором стоит на месте с точностью до пикселя.

Второе: `sceneRect` был равен рамке содержимого. Пока лист помещается
в окно, полос прокрутки нет вовсе — двигать нечего, и увеличение упирается
в один и тот же центр. Теперь вокруг схемы оставлено поле в половину её
размера с каждой стороны (`GraphicsView.SCENE_MARGIN`), и вид тянется всегда.
Поле считается от размера схемы, а не окна: иначе появление полосы прокрутки
меняло бы размер окна, а тот — поле.

Заодно схему стало можно просто тащить левой кнопкой, как в любом редакторе:
рамку выделения она не тянет (выделять на сцене нечего, устройства выбираются
щелчком), а щелчком считается нажатие, после которого кнопку отпустили,
не сдвинув дальше четырёх пикселей.

**Третий проект — станция мойки MCA1** (`doc/inputMCA`, 154 листа,
356 устройств). Lua читались и раньше, а вот находилось по ним мало:
206 устройств из 356 по всему файлу и одно-единственное на листе общей
обвязки. Причин три, и все три в разборе.

*Имя без техобъекта.* Разбор имени требовал объекта впереди
(`^(.+?)<ТИП><номер>$`), а в этом проекте 22 устройства названы просто
`V1`, `LT2`, `FQT1` — общая обвязка станции: танки щелочи, кислоты и воды,
их уровни, дозаторы, расходомер. Такие имена не разбирались вовсе,
устройство молча выпадало из работы, а `FQT1` разбирался ещё и неверно —
как объект `F` с устройством `QT1`. Теперь объекта в имени может не быть
(`^(.*?)…`), а сопоставление ищет такие устройства по точному совпадению
подписи — последним, после всех, у кого владелец есть, и только если
подпись на листе одна и не занята. Окно показывает их группой «Без объекта»
(`scene_painter.object_title`).

*Четыре типа вне списка.* `FS`, `WT`, `WC`, `LC` числились вне
`DEVICE_TYPES` — теперь они в списке. На двух
прежних проектах это не меняет ничего (проверено разбором всех имён),
в MCA1 добавляет три реле потока.

*Уставки объекта только рабочие.* Разбор `main.objects.lua` читал
`par_float` и не знал про `rt_par_float`. В MCA1 объекты описаны только
вторым — 420 параметров на три объекта терялись целиком. Теперь читаются
оба; у рабочих к номеру приписывается «rt», чтобы номера двух списков
не сталкивались.

Итог по проекту: **228 устройств из 356** вместо 206, лист общей обвязки —
20 вместо 1, и отчёт о расхождениях по нему пуст, кроме объектов с других
листов. Контрольный лист и mozzarella не изменились ни на число.

Что осталось за пределами разбора: в `main.objects.lua` этого проекта
у всех трёх объектов `modes = {}` — операций, состояний и шагов в файле нет вовсе,
поэтому список операций пуст и положение устройств в операции показывать
не из чего.

**Схлопнутая до нуля панель возвращается сама.** Границу можно утащить
до края — панель схлопывается, и ноль уезжает в настройки: следующий запуск
открывался уже без неё, а место, где она была, ничем не отмечено. Так пропала
панель сведений (`splitters/scene = [1596, 0]`), и выглядело это как «панель
убрали из программы». Теперь при запуске панель, схлопнутая раскладкой в ноль,
разворачивается обратно; спрятанное осознанно (`Ctrl+B`, `Ctrl+I`, `Ctrl+J`)
помнится отдельным признаком, и его видно галочкой в меню.

**Панели двигаются и убираются.** Левая панель была зажата между 240 и 420
пикселями: ни расширить, чтобы прочитать длинные имена, ни убрать, чтобы
посмотреть на схему. Теперь границы панелей тянутся куда угодно, двойной
щелчок по границе сворачивает панель и возвращает её в прежний размер
(`widgets.Splitter`), а `Ctrl+B`, `Ctrl+I` и `Ctrl+J` убирают и возвращают
левую панель, сведения и список операций целиком. Спрятанные панели
остаются спрятанными между запусками. Схему свернуть нельзя ничем — убрать
с глаз можно всё, кроме неё.

**Оформление одним листом стилей** (`theme.py`) — палитра названа один раз
и применяется ко всему окну: границы панелей видно и они подсвечиваются под
курсором, поля и списки одной формы, вкладки с полосой под выбранной, тонкая
прокрутка, под схемой серая подложка, чтобы белый лист читался листом. Смысл
цветных кнопок прежний (Lua — синяя, чертёж — зелёный, разметка — сиреневая),
но цвет берётся из палитры по свойству `accent`, а не пишется строкой стиля
рядом с кнопкой: одинаковые по смыслу кнопки расходились на пару оттенков.
Тема — только внешность: ни одного обработчика она не трогает, и проверки
интерфейса собирают окно без неё.

**Детекция** — читаются класс (`valve`/`sensor`/`pump`) и уверенность модели; NMS
по уверенности; объединение вложенных рамок; подпись достаётся одному устройству;
покрытие всего листа плитками; три профиля детекции.

**Структура** — общий `svg_geometry.py` вместо трёх копий (−525 строк); `config.py`
вместо хардкода; `markup_cache.py` (повторная разметка ~0 с); `check_pipeline.py`
как проверка.

`xml_viewer.py` разнесён: сначала на `workers.py` (потоки) и `widgets.py`
(виджеты), затем ещё на три — `xml_io.py` (чтение своего XML, без Qt),
`ui_panel.py` (сборка левой панели) и `scene_painter.py` (отрисовка схемы,
получает набор «что показывать» вместо восьми переключателей). Из 2407 строк
осталось 1965, самый длинный метод — 104 строки вместо 256. Смысл в том,
что разбор XML и отрисовка теперь проверяются без окна: 27 новых проверок.

**Отчёты** — расхождения чертежа и Lua (кнопка в GUI, `--report`); качество разметки;
граф связности секцией `Connections` в XML.

**Выгрузка в формат редактора мнемосхем** — то, что уходит в конечный проект.
Первая передача не отобразилась вовсе, и причина оказалась не в мелочах:
редактор читает **плоский массив элементов холста**, а уезжало дерево.
Его импортёр заворачивает объект в массив из одного элемента
(`Array.isArray(json) ? json : [json]`), из дерева получается один элемент
без типа — файл открывается, холст пуст.

Теперь `Ctrl+E` по умолчанию пишет `*.json` в формате редактора: линия чертежа —
элемент `line` (концы, центр, габарит, цвет), устройство — `circle` с именем,
техобъектом, артикулом и описанием, рамка техобъекта — четыре линии, имя
контура и подпись устройства — `text`. Контрольный лист A0 даёт 6178
элементов (5547 линий чертежа, 132 стороны рамок, 233 устройства,
233 подписи, 33 имени) и файл 4.6 МБ, лист 13 mozzarella — 1144.
Если холсту редактора это много, `CONTUR_HMI_LINES=pipes` убирает контуры
устройств (они и так нарисованы кружками) — остаётся 3259 элементов и 2.4 МБ,
`CONTUR_HMI_LINES=none` убирает чертёж целиком (631).

Три вещи разобраны по коду импортёра, а не на глаз:

- **координаты числами, 1:1 в пунктах PDF.** Проценты строкой он тоже
  понимает, но умножает на `CANVAS_W = CANVAS_H = 5000`; холст квадратный,
  а лист нет — в процентах A0 растянуло бы с 1.41:1 до 1:1. Пунктами
  A0 (3368×2384) входит в холст целиком и без искажения. Среди присланных
  образцов половина была как раз в процентах;
- **ключи уникальны и ссылки согласованы.** Импортёр раздаёт свои ключи,
  но `parentKey` и `children` переводит по карте старых, и ссылка на
  отсутствующий элемент остаётся битой. Здесь они выводятся из содержимого
  (`uuid5`): один и тот же лист даёт один и тот же файл;
- **`id`/`parentId` — настоящие `null`, `composition`/`isDefault` — настоящие
  `true`/`false`** (в образцах ходили строки `"null"` и `"false"`).

Размер символа пришлось ограничить: габарит берётся из кластера красных
линий, а кластер прихватывает соседние отводы — у 105 устройств из 233 высота
выходила до 482 пт вместо тридцати, и в редакторе такой «датчик» накрыл бы
пол-схемы. Сторона держится в пределах 0.5–1.5 от обычного размера символа
на этом листе (около 33 пт на A0).

Устройства рисуются кругами: многоугольнику нужен список точек, а какой они
системы координат — по образцам не понять (у многоугольника с `x=44` точки
идут от −20 до 80). Клапан от датчика отличается полями `device_type`
и `lua_name` — лишние поля импортёр сохраняет. Форма по классу модели —
`CONTUR_HMI_SHAPES=class`. Группы по техобъектам выключены по той же причине:
у группы дети живут в её системе координат, ошибка двигает всю схему
(`CONTUR_HMI_GROUPS=1`, координаты детей пересчитываются).

**Выгрузка для редактора несёт данные и собрана по спецификации импорта** —
то, ради чего файл и нужен. Раньше в нём была одна геометрия в пунктах листа:
редактор рисовал схему, про которую ничего не знал, и рисовал её криво.
Спецификация импорта объяснила почему, и разбор сошёлся с её правилами.

**Состояния каждого устройства.** У элемента редактора есть список `states`,
и там лежала одна заглушка «Нормальное». Теперь положение устройства в каждом
шаге каждой операции уезжает полем `contur_states`: `opened`/`closed`,
операция, состояние, шаг и его номер. На контрольном листе **1911 состояний
у 233 устройств из 64 операций**, на листе 13 mozzarella — 63 у 35. Своим
полем, а не штатным `states`: по их §7 в `states` полагается ровно одно
состояние с пустым `overrides`, иначе базовые `x/y/w/h` при отрисовке
игнорируются — восемьдесят состояний у клапана сдвинули бы саму схему.

**Масштаб и сетка — то, что чинит «размер кружков не тот».** Их холст
размечен сеткой 20, минимальный объект — две клетки, минимальный радиус
круга — 20. Мы слали пункты один к одному, кружок приезжал радиусом 14,
и редактор поднимал его сам. Теперь лист масштабируется одним коэффициентом
`k = 40 / обычный символ листа` (A0 — 1.277, лист 13 mozzarella — 1.297),
сдвигается в начало координат и садится на узлы: все 1278 объектов
контрольного листа стоят в узлах, радиусы кратны клетке, габарит равен двум
радиусам. Чертёж выровнен мягче, как они и просят: ортогональный отрезок
садится, если это смещает конец не больше чем на полклетки и не схлопывает
его (2921 из 5003), диагонали и звенья кривых остаются точными.

**«Линии обрываются» — три причины на стороне выгрузки.** Отсечение рамки выбрасывало
отрезок, если в поле листа попал любой его конец, и уносило 73 отрезка живого
чертежа из 252 (27 — красные контуры устройств); теперь чертёж уезжает
целиком, а рамка помечена полем `frame`. Кривые уезжали хордой — 784 штуки
с отклонением 3.27 пункта в медиане и до 6.3; теперь ломаной с допуском
в пункт (2112 звеньев). Четыре вырожденных отрезка приезжали точками —
больше не отправляются.

**«Ромбы» — `polygon` без списка `points`:** редактор строит в этом
случае правильный многоугольник по своему `sides`. Делал это выключенный
по умолчанию режим `CONTUR_HMI_SHAPES=class`, он убран целиком — различать
клапан и датчик можно по `device_type`, который едет с элементом.

Остальное по спецификации: рамка техобъекта стала `rectangle` вместо
четырёх линий (132 → 33 элемента), у группы появилась рамка-ребёнок (без неё
габарит группы схлопывается), кегли 12 и 16 вместо 8 и 10 пунктов, `color`
уехал в `contur_color` (в редакторе это заливка), толщины линий ступенями 1/2/3,
`composition` не отправляется, у `meta` стоит `visible: false`.

Вместе с этим в файл доехало то, чего в нём не было вовсе: поля XML целиком
у устройства, состояние в выбранной операции (`current_operation_id`
передавался и молча игнорировался), связность на самих элементах
(`pipeline_id` у линии, `connected_devices` у 164 устройств из 233), надписи
чертежа (779 элементов `text` с `drawing`) и элемент `meta` с тем, для чего
в XML заведены секции: 767 труб, 250 связей, 4713 точек сопряжения,
64 программы операций.

Контрольный лист: **8353 элемента**, холст 4340×3060 из их 5000×5000; лист 13
mozzarella — 1750 и 3120×2220. Приёмка по их списку самопроверки (§10)
выполняется кодом — `hmi_validate.py`, отдельным шагом `check_pipeline`
и сама по себе: `python hmi_validate.py выгрузка.json`. **Оба контрольных
листа проходят её без замечаний.**

Переделка нашла две свои дыры. `check_pipeline` разбирал `main.objects.lua`,
но не загружал разобранное — весь путь «состояние устройства в операции»
проходил мимо проверки. И у детей группы сдвиг листа вычитался дважды.

Правила отрисовки целиком — в `PROJECT.md`, §6.2.

**Выгрузка отдаёт функциональную часть, а не разметку.** Контуров, их имён,
границ и цветных кружков над устройствами в файле больше нет: это выводы
конвейера о чертеже, а нужен сам чертёж и данные. Обозначения Eplan никуда не делись — они часть чертежа
(779 надписей на A0). На приложении это не сказалось: в окне рисуется всё
по-прежнему, выключены только каналы выдачи.

**Устройство стало цельным объектом.** Был кружок-маркер поверх россыпи
отрезков, среди которых ничего не выбрать. Стало: `group` с `contur_device`,
внутри — прозрачный прямоугольник, держащий габарит (без него группа
схлопывается при первом перетаскивании), и линии его же символа с чертежа
в локальных координатах. На самой группе висит всё: имя из контроллера,
техобъект, тип, артикул, теги, состояния по операциям, соседи по трубам.
Устройство привязано к своему символу по координате — сопоставление уже
поставило её в центр кластера красных линий; прежний поиск по имени был
неверен и для размера, коротких имён 27 на 233 устройства. Свой символ есть
не у всех: на A0 у 174 объектов из 233, на листе 13 mozzarella — у 26 из 35.

**Теги доехали** — то, чего в файле не было вовсе. Сопоставление брало
из описания устройства имя, артикул, категорию и подтип, а каналы
ввода-вывода выбрасывало прямо в `device_matcher`: `DI`/`DO`/`AI`/`AO`
с адресом в контроллере (`node`, `offset`, `module_offset`, `physical_port`,
`logical_port`), `par`, `rt_par` и `prop` не доходили ни до одной выгрузки.
Теперь они едут полем `contur_tags`.

Рядом, в `meta`, появилось остальное про объекты: узлы контроллера (7),
сигналы проекта (147 — секция была в выгрузке всегда, а разбор
`main.objects.lua` её пропускал) и уставки, свойства, состав оборудования
и системные параметры техобъектов. Техобъект листа связывается с описанием
через свои устройства: имя контура (`LA_TANK1`) и имя объекта в описании
(«Линия наполнения ALPMA O») — разные вещи, а состояние устройства несёт
идентификатор объекта.

Контрольный лист: 8353 → 8287 → 7004 элемента, 233 объекта устройств;
лист 13 mozzarella — 1655.
Вид устройства переключается: `CONTUR_HMI_DEVICES=object` (по умолчанию),
`circle` (прежний кружок) или `none`; разметка возвращается
`CONTUR_HMI_CONTOURS=1` и `CONTUR_HMI_LABELS=1`.

**На месте устройства — готовая фигура библиотеки.** В сцене редактора
`MOZARELLA_01` уже нарисованы клапан, датчик и ёмкость. Рисовать их заново
значит отдавать схему, непохожую на сами мнемосхемы редактора, поэтому
теперь внутри объекта устройства стоит библиотечная фигура, а не красные
отрезки с чертежа Eplan.

Каталог собирается из этой выгрузки (`tools/extract_symbols.py`): фигура —
это то, что собрано в группу или встречается не реже трёх раз; вершины
приводятся к общему порядку, иначе один и тот же прямоугольник, нарисованный
с разных углов, даёт две разные фигуры (так и было — 21 клапан
распадался на 14 и 7). За образец берётся самый частый размер: у датчика
это круг r60, а не обод аппарата r780 той же формы. Результат — шесть
фигур в `hmi_symbols.json`; насос и «бабочка» ручного клапана лежат
в коде (`hmi_symbols.BUILTIN`), потому что цельной фигурой в сцене их нет.

Выбор по обозначению: `V`/`VC` — клапан (лежачий или стоячий, видно
по вытянутости кластера красных линий), `V` без имени в Lua — ручной
(у него нет ни одного канала ввода-вывода), `M` — насос или мешалка,
датчики — кружок с обозначением внутри. Фигура нашлась всем 233
устройствам A0 и всем 35 на листе 13.

Насос и мешалку пришлось разделить: обозначение общее (`M`), а Eplan
рисует их по-разному — насос стоит на трубе кругом с рабочим колесом,
мешалка это кружок с обозначением плюс лопасть в танке. На A0 из
пятнадцати `M` восемь мешалки, и все восемь приезжали насосом. Различаются
по описанию из Lua (`CONTUR_HMI_AGITATOR_NAMES`). Сам насос тоже
перерисован по чертежу, а не выдуман: круг, вписанный треугольник остриём
по потоку и горизонтальный диаметр, все вершины на круге и в узлах сетки.

Размер сменил масштаб всего листа: библиотечная фигура нарисована на шести
клетках, а лист растягивался под кружок в две. Теперь `k = 120 / обычный
символ` (A0 — 3.83), и множитель каталога выходит единицей: фигура приезжает
точь-в-точь как нарисована, все узлы на сетке. Побочный итог — A0 занимает
12920×9160 при сетке редактора 5000×5000; приёмка печатает про это
предупреждение, а не замечание, иначе она перестала бы ловить настоящие
поломки. Сама сцена редактора занимает 6360×5820, так что за 5000 выходит
и она; размер меняется числом `CONTUR_HMI_SYMBOL_CELLS` (6 / 3 / 2 клетки).

Красные линии устройства, получившего фигуру, не отправляются вовсе —
иначе символ Eplan просвечивал бы сквозь библиотечный клапан: чертёж A0 похудел
— 2367 отрезков символов Eplan заменились 1084 примитивами каталога,
и файл похудел с 8287 элементов до 7004. Сам чертёж прежний: 4674 отрезка.

Имя фигуры уезжает полем `contur_symbol`, её примитивы помечены
`contur_symbol_part`: увидев их, редактор вправе выбросить эту отрисовку
и поставить свой компонент — данные лежат на самой группе и подмены
не замечают. Пока готовой библиотеки компонентов нет, ничего делать не надо.

Ёмкость техобъекта (`TANK`, `COAG`, `CIP` в имени) рисуется библиотечной фигурой
по границам контура: корпус тянется, патрубки остаются своего размера,
иначе на техобъекте 3880×3040 патрубок в клетку раздувается до полутысячи.
Появляется только там, где чертежа нет: с чертежом аппарат нарисован
дважды.

**Выгрузка PlantGeometry в JSON** — состав целиком (техобъекты с контурами
и устройствами, точки сопряжения, трубы, связи, разметка листа строкой в поле
`svg`), расширение `*.plant.json`. Редактор его не читает — это для
потребителя, которому нужны трубы и связи. Отличается от XML только запись:
числа вместо строк «62.064%», границы массивами, счётчики не дублируются.
На контрольном листе A0 весит 2.4 МБ против 2.6 МБ у XML.

Формат выбирается расширением (`exporters.py`): `Ctrl+E` предлагает `*.json`,
`*.xml` и `*.plant.json`, у пакетной обработки ключ
`--format xml|json|plant-json|both`.

Смысл сделан не в самом формате, а в том, чтобы каналы выдачи не разъехались:
разбор SVG, координаты, точки сопряжения и трубы вынесены из `xml_export`
в общий `export_scene.py` (тот же блок был скопирован и в `postgreSQL_export`,
третья копия означала бы три разных ответа об одном листе). XML после переделки
совпал с прежним побайтово на настоящем листе 1.1 МБ. Совпадение форматов
сверяется дальше само: на контрольном листе — шагом `check_pipeline`
(«JSON описывает тот же лист»: 233 устройства, 767 труб, 250 связей — как
в XML), на втором эталоне mozzarella — им же, на синтетическом —
`tests/test_json_export.py`.

Переделка заодно показала дыру в проверках: выгрузка с выбранной операцией
не покрыта ничем — ни одна проверка не задавала `current_operation_id`,
хотя это целая ветка кода (состояние устройства в операции, секция
`CurrentOperationInfo`). Сломать её при переносе можно было незаметно: экспорт
ловит любую ошибку и отчитывается «не удалось экспортировать данные», без
причины. Здесь поломку поймал линтер, а закрыта она теперь проверками
на оба формата сразу.

**Схема доехала, но рисовалась криво** — разобрано по присланному файлу
и коду импорта. Три причины, и все три на стороне выгрузки.

Круг был овалом: габарит устройства берётся из скопления красных линий,
и при `w ≠ h` редактор строит фигуру по габариту — на листе mozzarella так
рисовались 26 устройств из 35. Теперь `w = h = 2·radius`.

Контуров, их имён и подписей устройств в файле не было вовсе (контуры — только
по флагу, подпись — строкой в `label`), то есть показать их редактор физически
не мог. Теперь рамка техобъекта уходит четырьмя линиями (тип `line` рисуется
заведомо, `rect` в выгрузках редактора не встречается),
имя контура и подпись устройства — элементами `text`, строка продублирована
в полях `text` и `label`.

Цвета не передавались: у всех кружков было `bg: "transparent"`. Палитры
переехали из окна в `config.py` — теперь выгрузка красит устройства по типу
и рамки по техобъекту теми же цветами, что окно. Попутно ушла мелочь: цвет
контура выбирался через `hash(str)`, который рандомизируется при каждом
запуске Python, и у объекта менялся цвет от запуска к запуску.

«Кружок рядом с прямоугольником» — не ошибка: прямоугольник это контур
устройства с чертежа, кружок — маркер, и в окне они лежат друг на друге.
Порядок элементов в массиве теперь повторяет слои окна: рамки → чертёж →
устройства → подписи.

Причина смещения кружков подтвердилась: в редакторе `x, y` круга — левый
верхний угол габарита, а в выгрузке центр, отсюда сдвиг ровно на радиус.
Точка привязки теперь расписана по типам (линия — середина, круг — центр,
текст — левый верхний угол строки), а не «центр у всех», как было в первой
редакции.

Заодно нашлась своя дыра: в режиме `CONTUR_HMI_GROUPS=1` в файле
не было ни одного текста — подпись пропускалась у всех,
у кого есть родитель, а имя техобъекта не выгружалось вовсе. Теперь детьми
группы становятся устройство, его подпись и имя, координаты локальные, связь
двусторонняя: холст рисует детей по массиву `children`, и ссылки только вверх
ему мало. A0 в этом режиме даёт 6076 элементов и 30 групп (у трёх контуров
из 33 нет сопоставленных устройств — их имена остаются верхнеуровневыми).

Правила отрисовки целиком — в `PROJECT.md`, §6.2: система координат, слои,
что каким элементом рисуется, цвета, переключатели и контрольные числа
для приёмки.

Обратное чтение JSON приложением не сделано: `Ctrl+Shift+X` открывает только XML.
Формат редактора обратно не читается тем более — он про холст, а не про эти данные.

**Отчёт о пропажах стал означать пропажи** — на листе 13 mozzarella «есть в Lua,
нет на чертеже» было 66, стало 5. Две причины, обе не про распознавание.
Во-первых, устройство, описанное и в `main.io.lua`, и в `main.wago.lua`, считалось
дважды: слияние склеивало списки подряд (1298 записей при 771 имени, 13 узлов
при семи), и полное описание затиралось усечённым — артикул `XB4BS8445` вместо
`SE.XB4BS8445`. Теперь первая запись главная, последующие дополняют её пустые
поля. Во-вторых, 36 оставшихся строк — сигналы ввода-вывода (`DI`, `DO`, `AI`,
`AO`): каналы контроллера, а не оборудование, а весят они 38% молокохранилища
и 63% mozzarella. На технологических листах их не рисуют вовсе, и там они
считаются отдельной строкой, как `WATCHDOG`.

Но «не рисуются» — свойство листа, а не проекта, и это стоило отдельной поправки:
сначала вывод был сделан по двум технологическим листам, а прогон по всем 265
страницам показал 117 сопоставленных сигналов из 147 — на страницах 5–14, листах
обмена сигналами, где на девяти из десяти вообще ничего, кроме сигналов, нет.
Теперь про это спрашивают сам лист: сопоставился ли на нём хоть один сигнал.
Да — лист сигнальный, и несопоставленный сигнал здесь настоящая пропажа. Нет —
сигналов тут не рисуют.

Отдельно отсеиваются **подписи линий**: обозначение, повторяющее имя своего же
контура, — это красная стрелка «`M7` → К ПОУ 1», а не устройство. На контрольном
листе таких пять; «есть на чертеже, нет в Lua» 11 → 6. Оставшиеся шесть по делу:
пять кружков `-FC1` (регулятор при расходомере, входов-выходов нет — оттого нет
и в `main.io.lua`) и `MCA1V1101` — настоящий клапан, которого в конфигурации
контроллера нет вовсе.

**Связь этапов** — разметка получает имена от сопоставления, а не только из сырых
подписей: опознанных кластеров 174 → 189, из них 46 с полными именами.

**Подписи над кромкой контура** — сопоставлено 221 → 233, «есть в Lua, нет на
чертеже» 12 → 0. Двенадцать клапанов CIP-коллектора (`M1V91`…`M6V92`) числились
пропавшими, хотя нарисованы на всех шести рядах: Eplan ставит обозначение над
символом, клапан сидит на самой верхней кромке ряда, и подпись выходит за контур
на 2–8 пт. Расстоянием это не разобрать — ряды отстоят на 11–14 пт, и подпись
бывает ближе к чужому ряду сверху, чем к своему. Решает направление (подпись
стоит над своим устройством) плюс два ограничителя: контур должен ждать такое
устройство и место не должно быть занято. Отбор держит именно ожидание: из 24
подписей вне контуров берутся ровно 12 нужных, а двенадцать подписей самих рядов
(`+M1`…`+M12` на левом поле) отсеиваются. Такие привязки помечены уверенностью
0.9 — имя совпало точно, контур выведен по расположению.

**Надёжность** — 225 проверок на разобранные места, гоняются в начале
`check_pipeline`; эталон показателей контрольного листа, сверка при каждом
прогоне; линтер `ruff`; пакетная обработка многостраничных PDF.

**Выгрузка в базу** — 3.6 → 0.9 с: связи и точки сопряжения уходят пачками,
а не по строке (замер на живой базе в Docker: 4713 точек стоили 2.94 с, стали
0.38 с). Контуры и устройства оставлены построчными — возвращают идентификаторы
и стоят сотые доли. Вся выгрузка одной транзакцией (фиксировалась по таблицам,
и сбой оставлял в базе обрывок); при повторной выгрузке спрашивается «дописать
или заменить» — связи и точки сопряжения не защищены от повтора, а колонки
листа в схеме нет и добавить нельзя; `contour_id` у точек сопряжения заполняется
(колонка была всегда пустой); окно показывает числа выгруженного.

**Журнал** — `output/contur.log`, вывод раздваивается: остаётся в консоли
и пишется в файл, туда же попадают предупреждения Qt и трассировки
необработанных ошибок. До этого собранное приложение было немым: `console=False`,
`sys.stdout` равен `None`, и все двести `print` уходили в пустышку.

**Закрытие окна** — дожидаются все шесть фоновых потоков, а не один; срок общий,
чтобы окно не замирало надолго; если что-то не остановилось, спрашивается
разрешение вместо аварийного завершения посреди записи в базу.

**Детекция на OpenVINO** — 73 → 53 с при том же результате. Совпадение проверено
не числами, а побайтово: разметка контрольного листа даёт тот же хеш, что в эталоне.
Требует `pip install openvino` и выгрузки `python tools/export_openvino.py` —
повторять после каждого переобучения модели. Без установленного пакета
выгруженная модель игнорируется, приложение остаётся на PyTorch; отключить
вручную — `CONTUR_YOLO_ENGINE=torch`.

Встроенная графика быстрее втрое (24 с), но десять рамок из 257 расходятся
на 34–1202 пикселя, поэтому устройство задано жёстко `intel:cpu`.

Две грабли выгрузки, обе всплывают не при выгрузке, а уже в работе:
по умолчанию модель выгружается под один кадр (`got [4,...] expecting [1,...]`),
а одного `batch=4` мало — последняя из 234 плиток идёт неполной пачкой
(`got [2,...] expecting [4,...]`). Нужна изменяемая размерность.

**Покрытие по всему проекту** — измерено впервые, прогоном по всем 265 страницам
(`batch_process --no-markup`, 246 с). Устройства нашлись на 87 страницах из 265,
остальные — не технологические листы.

|---|---|
| Имён в Lua | 401 |
| Не устройства (`WATCHDOG`) | 9 |
| Сигналы `DI`/`DO`/`AI`/`AO` | 147, из них найдено **145** |
| **Рисуемых устройств** | **245** |

Это и есть настоящая мера полноты: числа отдельного листа её не заменяют, потому
что техобъект разложен по нескольким листам. Подробности — `output/_coverage_all/coverage.json`.

**Подпись контура и вложенная рамка** — рисуемых устройств найдено 242 → 244
из 245, сигналов 117 → 126 из 147. Разрыв объяснился не распознаванием
устройств, а именем контура. На листе 5 подпись «`+CAB2`» стоит в 4 пт над
кромкой шкафа, но внутри шкафа есть тесный квадратик «`-Y1`» (сигнализация),
и до его угла 73 пт — меньше порога 200. Контуры разбираются от меньшего
к большему, квадратик успевал забрать подпись себе, шкаф оставался безымянным,
и ни одно его устройство не сопоставлялось; то же с `CAB3`. Мера расстояния
брала ближайший отрезок, то есть тянулась и по диагонали от угла; теперь
подпись должна попадать хотя бы в одну полосу контура — стоять над ним,
под ним или сбоку. Помогло на тринадцати листах, девять из них давали ноль
(страниц с сопоставлениями 67 → 76), а «есть на чертеже, нет в Lua» по проекту
493 → 437. Заодно ушли три ложных имени контуров: «`Line2`», «`PRIEM/13`»
и «`MCC1-W(`» — обрывки ссылок и обозначения провода.

Вторым заходом добавилась вложенность: на листе 14 подпись «`+LINE_M4`» стоит
в 25 пт правее своего блока и в 43 пт левее тесной рамки, вложенной в соседний
блок `LINE_M6`. Проверка «не по диагонали» тут не спасает — подпись ровно сбоку
от обеих. Eplan ставит обозначение блока вплотную к его кромке, но никогда
за пределами объемлющего блока, поэтому вложенный контур вправе брать только
подписи изнутри своего блока. Семь сигналов `LINE_M4`, сигналов 126 → 133.

**Владелец из штампа листа** — сигналов 133 → 145 из 147. Полное обозначение
по Eplan это «`=установка +расположение -устройство`», и расположение берётся
из блока «`+…`», которым устройство обведено, а если блока нет — из штампа
самого листа. Второе не разбиралось вовсе: на листе 5 двенадцать сигналов
`PRIEM` (`DI16`…`DI21`, `DO16`…`DO21`) стоят столбцом посреди листа, контуров
вокруг них нет, и ни один не сопоставлялся. Штамп читается по ячейке «`+`»:
знак стоит отдельным спаном, содержимое — той же строкой правее; знаков «`+`»
на листе несколько, штамп — самый нижний.

Отбор держат три условия: установка листа должна быть техобъектом из Lua,
объект должен ждать устройство с таким обозначением, и обозначение должно
встретиться вне контуров ровно один раз. Последнее существенно: на листе 34
вне контуров четыре подписи «`-SB1`», и без проверки одно устройство `MCC1SB1`
получило бы четыре привязки в разных местах листа. Помимо двенадцати новых
имён приём добрал 19 повторных привязок на монтажных листах, где подпись —
ссылка на клемму («`-G1:1.1`»); устройство там и правда присутствует,
на покрытие это не влияет. Уверенность таких привязок 0.8.

**Три ненайденных имени нарисованы, но под чужим владельцем** — `LINE_M10HL1`
есть на листе
240 как «`-HL1`», но внутри контура «`+CAB10`», а объекта `CAB10` в Lua нет
вовсе: в конфигурации лампа приписана к `LINE_M10`. Лист 75 говорит это прямым
текстом — «`+LINE_M10-DO103 Светодиод HL1`» рядом с «`+CAB10-HL1:x1`»: выход
контроллера принадлежит `LINE_M10`, а сама лампа стоит в шкафу `CAB10`.
Штамп того листа тоже даёт `CAB10`, так что и запасной канал не помогает.

То же с `MCA2AI1000` и `MCA2AO1000`: на листе 7 подписи «`-AI1000`»
и «`-AO1000`» нарисованы внутри блоков «`+MCA2LINE1`» и «`+MCA2LINE2`»
(по разу в каждом), а конфигурация приписывает их объекту `MCA2` — без
`LINE`. У соседнего `MCA1` те же сигналы названы `MCA1LINE1AI1000`
и сопоставляются без всяких оговорок.

Это третья причина, отдельная и от «не нарисовано», и от «нарисовано
на соседнем листе»: чертёж и конфигурация расходятся в том, чьё устройство.

**Второй проект** — приложение прогнано на `../doc/mozzarella_master_01`, которого
оно никогда не видело, и это сразу нашло две вещи. Список типов устройств снова
оказался неполон: не разбирались `VC`, `HA`, `TC`, `FC` — 13 устройств из 730,
то есть они не могли быть сопоставлены вовсе. И сама проверка конвейера видела
половину данных: файлов устройств бывает несколько (`main.io.lua` вместе
с `main.wago.lua`), окно грузит их вместе, а `check_pipeline` брал один —
из 1298 устройств видел 730. После обеих правок на листе сопоставлено 35
вместо 21. Полноту списка типов теперь держит `tests/test_device_names.py`
на обоих проектах сразу.

**Сборка** — проверена впервые за семьдесят коммитов и оказалась сломанной:
`lupa` при импорте перебирает файлы своей папки, выбирая самую новую сборку Lua,
статический анализ этого не видел, и приложение падало до появления окна —
разбор Lua в собранном виде не работал вовсе. Лечится `collect_submodules('lupa')`
в `.spec`. Сейчас собирается и запускается: журнал ложится рядом с exe
(`dist/МоеПриложение/output/contur.log`, первая строка «собрано: да»),
модель находится внутри сборки.

**Битый вход** — вместо текста библиотек (`Cannot open empty file: filename='C:/...'`,
`error loading code: [string "<python>"]:88`) человек видит объяснение: файл пуст,
это не PDF, ошибка синтаксиса Lua в такой-то строке. Скан объясняется отдельно —
он открывается без ошибки и даёт ноль сегментов. Битый файл больше не становится
текущим чертежом: раньше после отказа окно считало его загруженным.

**Ноль сопоставлений** — больше не отчитывается как успех. Чертёж молокохранилища
с Lua другого проекта давал зелёное «✅ Сопоставлено: 0» и окно «Успех»; выглядело
как поломка распознавания, а разобраться можно было только по журналу. Теперь
называется причина: сколько техобъектов на чертеже, сколько в Lua, сколько имён
совпадает, и если ни одного — что это похоже на файлы разных проектов. Случаи
«нет именованных контуров» и «Lua не загружен» разобраны отдельно.

**Кэш разметки** — предел 300 МБ (`CONTUR_CACHE_MAX_MB`), при переполнении уходят
записи, к которым дольше всего не возвращались. Раньше рос без предела: 470 КБ
на лист, около 120 МБ на проект из 265 листов, и старые записи не удалялись даже
при смене версии формата. Очистка целиком — меню «Обработка».

**Скорость приложения** — запуск 2.65 → 0.5 с (`ultralytics` тянул `torch` при
старте, даже когда разметку не запускали); минус 3.5 с с каждого прогона разметки
(страница рендерилась в PNG второй раз только ради своего размера в пикселях).

**Работа в окне** — перерисовка больше не сбрасывает масштаб; координаты курсора
и устройство под ним доходят до статус-бара; разметку можно прервать, видно
проценты и остаток; горячие клавиши на `Ctrl+…` вместо одиночных букв; поиск
по устройствам с подсветкой на схеме; панель сведений об устройстве
и об операции по щелчку; слои,
легенда, мини-карта; переход по
листам; память настроек и сеанса; перетаскивание файлов; один диалог PostgreSQL
вместо четырёх окон подряд, выгрузка в фоне.

## Что проверено и НЕ подтвердилось

Чтобы не переделывать заново:

- **Подгонка масштаба детекции почти не окупается.** Доведение относительного размера
  символа до обучающего (0.087 → 0.204) даёт +10 уверенных детекций при пятикратном
  времени. Выигрыш только в чистоте: сомнительных 30 → 12. Сквозной замер показал,
  что «идеальный» масштаб не лучший: по опознанным устройствам выигрывает 300 dpi.
- **Принадлежность линии по перекрытию ничего не изменила** — оба критерия дали
  одинаковую классификацию всех 5015 линий: трубы упираются в устройства, а не
  проходят сквозь них.
- **Относительные допуски не нужны на этих чертежах** — Eplan рисует символы
  фиксированного размера: 32.8 пт на A0 и 33.8 пт на A3, множитель ≈1.
- **Обрезка по штампу не нужна** — правый нижний угол занят настоящим оборудованием.
- **Полная привязка к векторным компонентам избыточна** — `device_centers` уже даёт
  геометрию устройства из красных сегментов.
- **«Десятки неопознанных устройств» были ошибкой метрики.** Отчёт показывал число
  кластеров геометрии (189) вместо числа подписанных рамок (251 из 257). Исправлено;
  разрыв в разметке оказался равен нескольким слабым детекциям.
- **«Сопоставлено 221 из 401» сравнивало несравнимое.** Разобрано по причинам:
  9 имён — не устройства (`WATCHDOG`), 159 принадлежат 23 техобъектам с других
  листов проекта, и на этом листе есть ровно 233 устройства. Все 233 теперь
  сопоставлены; узкого места в сопоставлении на этом листе не осталось.
- **Пять «пропавших» устройств листа 13 mozzarella не пропадали.** У объекта `CIP`
  на этом листе нарисован один клапан из пяти (`V7`, он сопоставлен), остальные
  на других листах; у `LA_TANK1` есть `V101`, но не `V102`. Техобъект разложен
  по нескольким листам, и по одному листу отличить «не нашли» от «нарисовано
  в другом месте» нельзя в принципе. Проектное число даёт только `batch_process`
  (раздел «ПОКРЫТИЕ», `coverage.json`); раздел отчёта переименован в «нет на этом
  листе» и сам говорит об этом.
- **Интерфейс не тормозил — там нечего было ускорять.** Замерено: загрузка подложки
  SVG (1.1 МБ) 0.04 с, полный разбор геометрии для отчёта 0.12 с, загрузка весов
  модели 0.0 с. Медленными оказались только запуск и повторный рендер PNG — оба
  исправлены. Кэшировать модель между прогонами смысла нет.
- **Название листа по размеру шрифта не определяется** — в штампе почти весь текст
  одного кегля 8.8. Работает отбор по длине строки с отсевом начинающихся со строчной
  буквы (это обрывки примечаний) и подписи «Примечания к чертежу».
- **Обозначение Eplan `=TM+PRIEM/1` есть не везде** — найдено на 14 листах из 60,
  как признак страницы не годится.
- **Выбирать пару «контур ↔ подпись» по общему счёту нельзя.** Напрашивается
  вместо перебора «от меньшего к большему» собрать все пары и раздавать
  подписи от самой уверенной. Контрольный лист от этого ломается: высокая
  колонка `[408, 604, 913, 2231]` перетягивает на себя подпись `TANK1` у её
  собственной рамки (подпись лежит внутри колонки, до её кромки 13 пт против
  8 пт до рамки) и собирает по одному «`-V1`» с каждого из 12 рядов —
  13 ложных сопоставлений. Порядок «от меньшего к большему» там как раз нужен,
  поэтому лечится не он, а мера расстояния.
- **Ссылки Eplan третьим каналом сопоставления ничего не закрывают.** Приём
  общий — полное обозначение «`+расположение-устройство`» встречается
  на 131 листе из 265, всего 1896 ссылок, 343 разные пары, и 251 пара (73 %)
  даёт настоящее имя из Lua, покрывая 251 имя из 401. Но три ненайденных
  имени не закрывает ни одна: у `LINE_M10HL1` ссылки говорят «`+CAB10-HL1`»
  (лампа стоит в шкафу) и «`+LINE_M10-DO103`» (выход контроллера принадлежит
  линии) — это две разные пары, а связывает их только текст описания
  «Светодиод HL1». У `MCA2AI1000` и `MCA2AO1000` похожих ссылок нет вовсе.
  То есть канал годится как ещё одно подтверждение того, что уже нашла геометрия,
  а не как источник новых сопоставлений.
- **Владельца из штампа нельзя раздавать без проверки на повтор.** На листе 34
  вне контуров четыре подписи «`-SB1`», и одно устройство `MCC1SB1` получило бы
  четыре привязки в разных местах листа. Берётся только обозначение,
  встретившееся вне контуров ровно один раз.

## Что дальше, по убыванию пользы

Разрыв покрытия закрыт: из 392 рисуемых имён (245 устройств и 147 сигналов)
не найдены три, и все три нарисованы — просто под чужим владельцем. Оставшееся
ниже — уже не про полноту распознавания.

1. **Два вопроса по размеру сцены открыты.** Нужна ли печать 1:1 — если да,
   клетка должна равняться миллиметру, лист A3 становится 8400×5940,
   а библиотеку приходится тянуть на ×1.1, и её узлы встают на 22 единицы
   вместо 20. Второй — разрешение экрана оператора: от него считается, с какого
   зума читается подпись. Фигуры кнопки, лампы и сирены к этому моменту
   нарисованы и лежат в каталоге.
2. **В библиотеке недостаёт мешалки, кнопки, лампы и сирены.** Насос
   в библиотеке шаблонов есть, и сразу тремя видами (центробежный, вакуумный,
   мембранный) — нарисованный здесь остался только на случай без каталога.
   Мешалки в библиотеке нет: она по-прежнему заимствует кружок датчика
   (`contur_symbol_origin: "contur"`) — на чертеже Eplan рисует её именно
